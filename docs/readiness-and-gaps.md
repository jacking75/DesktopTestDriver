# DesktopTestDriver에 더 필요한 기능

## 결론

**기본적인 앱 조작 기능은 있지만, 제품 시험 전체를 맡기기에는 아직 부족하다.** 앱 실행·키보드 입력·마우스 클릭·창 정보 조회·시나리오 실행 코드는 있다. 실제 실행 검증은 아직 마치지 않았다.

PC끼리는 정상적으로 통신한다고 가정한다. 아래는 시나리오로 앱을 조작하고, 결과를 확인하고, 실패했을 때 정리하기 위해 더 필요한 기능이다.

RemoteAssist는 사용 예다. DesktopTestDriver는 여러 제품에서 공통으로 쓸 기능을 제공하고, 각 제품의 시험 순서와 성공 조건은 사용하는 프로젝트가 작성한다.

아래 **구현 방법은 앞으로 개발할 설계**다. 현재 지원하는 사용법은 [시나리오 작성 규약](scenario-authoring.md)에 있다. 여기서 제안하는 명령·설정 필드를 지금 시나리오에 넣으면 실행되지 않는다.

구현 전체에서 다음 기준을 함께 적용한다.

| 구분 | 구현 기준 |
|---|---|
| Controller | 여러 PC의 실행 순서, 조건 판정, 결과 수집, 정리 진행을 관리한다 |
| Agent | 해당 PC의 사용자 세션에서 앱 실행·입력·관측을 수행한다. 상시 감독 프로세스인 `PersistentAgent`와 시험마다 실행하는 Client·Watchdog를 구분한다 |
| 별도 프로그램 | 제품별 화면 판독, 서비스 조작, 설치·복구처럼 제품 지식이나 별도 권한이 필요한 작업을 담당한다 |
| 시험 식별 | 시나리오 한 번의 실행에는 `executionId`, 각 PC의 작업에는 기존 `runId`를 쓴다. 여러 PC의 `runId`는 서로 다르며 `executionId`로 묶는다 |
| 문법 변경 | 새 필드와 실행 의미는 `schemaVersion: 2`로 추가한다. 버전 1의 기존 동작을 유지하고, 미지원 버전은 실행 전에 거부한다. 통신 계약 변경 시 Controller·Agent의 지원 여부도 시작 전에 검사한다 |
| 결과 판정 | 명령이 실행됐다는 사실과 제품 기능이 성공했다는 사실을 구분한다. 실제 관측값이 기대 조건을 만족해야 통과한다 |

## G01. 시험을 시작해도 되는지 확인

**문제:** 설정 파일에 복구 준비가 되어 있다고 적혀 있는지 검사하는 것과, 실제로 실패 후 복구할 수 있는지 확인하는 과정이 충분히 연결되어 있지 않다. 설정 검사를 통과해도 앱이나 복구 준비가 끝나지 않은 상태에서 시험을 시작할 수 있다.

**만들 기능:** 입력을 보내기 전에 시나리오에서 선택한 준비 조건을 검사한다. 각 검사는 실패 시 차단, 경고 후 진행, 검사 생략 중 하나로 설정한다. 대상 PC·사용자·앱·결과 저장·복구 준비를 확인할 수 있게 하되, 확인 수단이 없다는 이유만으로 모든 시험을 막지 않는다. 수행한 검사 결과는 지금 실행할 시험과 연결한다.

**좋아지는 점:** 준비 누락을 실제 화면 조작 전에 발견한다. 잘못된 앱을 조작하거나, 실패 뒤 정리하지 못하는 시험을 시작하는 일을 줄인다.

### 구현 방법

1. **설정 검사와 실행 직전 검사를 분리한다.** 기존 `scenario-check`는 파일·참조·허용 명령만 검사한다. `ScriptScenarioRunner.Run`에는 모든 역할의 `begin`이 끝난 뒤, 첫 앱 실행·입력 전에 준비 검사 단계를 추가한다. 시나리오에서 `required`로 정한 검사에 실패하거나 그 검사를 수행할 수 없을 때만 준비 실패로 차단하고, 이미 시작한 작업을 정리한다.
2. **검사별로 실행 여부와 실패 처리를 정한다.** `required`는 실패·확인 불가 시 차단, `warn`은 검사 후 문제가 있으면 경고를 남기고 진행, `skip`은 검사 자체를 호출하지 않는 방식이다. 사용자 일치·디스크 여유·별도 복구 확인 등의 항목에 적용한다. 아직 실행하지 않은 앱의 창이 존재할 것을 요구하지 않으며, 기존 앱에 연결하는 시험일 때만 프로세스와 창을 사전 확인한다.
3. **복구 실측 검사를 별도 선택 항목으로 둔다.** 필요할 때 결과 폴더의 쓰기·읽기·삭제, 저장 공간, 전용 시험 앱을 이용한 입력 해제·프로세스 종료를 확인한다. 이를 매 시험에 강제하지 않는다. 관리자 화면 등 독립 복구가 필요한 시험은 해당 계획에서 VM 콘솔·KVM 확인을 `required`로 지정한다. 일반 앱의 입력 시험에 독립 복구 장비를 요구하지 않는다.
4. **준비 결과를 이번 실행에 묶는다.** 결과에 `executionId`, `runId`, 설정 해시, 시나리오 해시, 확인 시각·만료 시각을 저장한다. 수행한 검사는 실행 직전에 다시 대조하고, 오래된 결과는 해당 검사의 모드에 따라 재확인·경고·차단한다. 생략한 검사는 통과로 꾸미지 않고 `skipped`로 남긴다. `RecoveryEvidence`에 문자열이 있다는 이유만으로 복구 검사가 통과한 것으로 처리하지 않는다.
5. **한 번에 통과/실패를 결정하는 검사를 항목별로 나눈다.** `Preparation.Check`의 세션·복구·저장 공간 검사를 각각 결과를 반환하는 함수로 추출하고, `ScriptExecution`의 검사 모드를 적용한다. 확인 프로그램 미설치나 조회 권한 부족은 `unavailable`, 조건 불충족은 `failed`, 생략은 `skipped`로 반환한다. 이 조회 오류가 일반 명령 실패처럼 즉시 `store.Stop`을 발생시키지 않게 분리한다. 준비 시간 초과 시에도 미완료 항목 각각의 모드에 따라 차단 또는 경고 후 진행을 결정한다. `IRecoveryAdapter.Probe`는 현재 `runId`를 받지 않으므로, 실제 복구 검사를 선택한 경우 이번 실행에 연결해 검증하도록 계약을 보완한다. 현재 `RunConfig.Validate`·`ScriptExecution.Validate`는 입력·앱 실행에 R1 및 `RecoveryEvidence`를 요구하므로, 버전 2의 일반 시험에서는 별도 복구 실측 증거가 없다는 이유만으로 차단하지 않도록 함께 변경한다. 버전 1은 기존 동작을 유지한다.

**완료 기준:** 같은 검사 실패를 넣었을 때 `required`는 차단, `warn`은 경고 후 진행, `skip`은 검사 미호출로 동작해야 한다. 확인 프로그램 미설치·조회 권한 부족·검사 시간 초과도 같은 규칙을 따라야 한다. 생략한 검사나 이전 실행의 증거가 준비 확인 성공으로 기록되면 안 된다.

### R1 복구의 의미와 검사 선택

R1은 이 프로젝트가 붙인 복구 수준 이름이다. **시험 도구가 보낸 입력을 해제하고, 도구가 이번 시험에서 실행·소유한 앱을 종료하는 수준**을 뜻한다. 예를 들어 Ctrl 키를 누른 상태에서 통신이 끊기면 키를 떼고 시험 앱을 종료하는 것이다. 기존 `InputController.ReleaseAll`·`Cleanup`, `OwnedApplications.Terminate`, Watchdog가 관련 동작을 담당한다.

R1만으로 원격 제품의 연결 종료, 서비스·설정 복원, PC 재부팅, OS 멈춤 복구까지 보장하지는 않는다. 제품 연결·설정 복원은 G04의 별도 정리 작업이고, 일반 Agent가 동작하지 못하는 잠금·관리자 화면 등의 독립 복구는 VM 콘솔·KVM을 사용하는 R2에 해당한다.

**“복구 동작이 구현되어 있음”과 “실행 전에 별도 복구 훈련으로 확인함”을 구분한다.** 일반 시험에서는 도구의 입력 해제·소유 앱 종료 기능을 유지하면서, 사전 복구 훈련은 생략할 수 있다. 생략하면 복구 가능성을 미리 실측하지 않았다는 기록만 남기며, 종료 시 실제 정리 작업은 계속 수행한다.

| 검사 모드 | 검사 결과가 실패 또는 확인 불가일 때 | 사용할 상황 |
|---|---|---|
| `required` | 본 시험을 시작하지 않는다 | 반드시 특정 사용자로 로그인해야 하는 시험, 독립 복구를 전제로 하는 시험 |
| `warn` | 결과와 이유를 경고로 남기고 시작한다 | 디스크 여유나 사용자 일치를 참고로 확인하되 시험은 진행할 경우 |
| `skip` | 검사를 호출하지 않고 `skipped`와 생략 사유를 남긴다 | 확인 프로그램이 없거나, 사전 복구 훈련이 필요 없는 경우 |

검사 모드는 사전 확인 정책이다. Agent 연결이 없거나 실행 파일이 없으면 실제 명령을 수행할 수 없고, `warn`·`skip`도 그 기능을 만들어 주지는 않는다. 머신·세션에 대한 명령 연결, 실행 허용 범위, 실행 중 Watchdog, 실제 미완료 정리 차단 같은 기존 실행 조건은 별도로 적용한다. 예를 들어 사용자 SID의 일치 여부는 생략할 수 있지만, 다른 세션에 명령을 보내기 위해서는 run 설정의 대상 세션 자체를 변경해야 한다.

버전 2에서는 `preflight`를 생략하면 사용자·디스크 여유 검사는 경고 수준으로, 별도 복구 훈련은 생략하는 기본 정책을 사용한다. 역할이나 개별 검사 설정을 생략해도 같은 기본값을 적용한다. 모르는 검사 이름·모드 오타는 설정 오류로 처리하며, `skip`에는 생략 사유를 요구한다. 경고·미확인·생략 내역은 본 시험의 기능 판정과 구분해 보고서에 보존한다.

### 시나리오 파일 작성 예

**시나리오에는 “무엇을 검사하고, 실패하면 진행할 것인가”를 선언한다.** 이를 위해 본 시험의 `steps`와 별도로 `preflight` 항목을 추가한다. 준비됐는지는 도구가 실제로 검사하고, 생략한 항목은 확인하지 않았다고 기록한다. 작성자가 `ready: true`를 적어 준비 검사를 대신하는 구조로 만들지 않는다.

다음은 대상 PC의 준비 상태를 확인한 뒤 RemoteAssist를 실행하고, 실행한 프로세스의 창이 나타나는지 확인하는 최소 예다. **버전 2로 구현할 제안 문법이며 현재 실행할 수 없다.** 마지막 단계의 긴 조건 대기는 G07의 제안 문법을 함께 사용한다. 이 예의 통과는 준비·앱 시작 확인을 의미하며, 제품의 원격 제어 기능까지 검증하는 것은 아니다.

`remoteassist-start.scenario.json`:

```json
{
  "schemaVersion": 2,
  "id": "remoteassist-start",
  "purpose": "대상 PC의 준비 상태를 검사한 뒤 RemoteAssist 실행과 창 생성을 확인한다",
  "roles": ["target"],
  "parameters": [],
  "maximumSeconds": 120,
  "preflight": {
    "timeoutSeconds": 20,
    "evidenceMaxAgeSeconds": 10,
    "roles": {
      "target": {
        "applications": ["remoteassist-host"],
        "checks": {
          "user": { "mode": "warn" },
          "evidence-space": {
            "mode": "warn",
            "minimumFreeBytes": 268435456
          },
          "recovery-probe": {
            "mode": "skip",
            "reason": "이번 시험에서는 사전 복구 훈련을 수행하지 않는다"
          }
        }
      }
    }
  },
  "steps": [
    {
      "id": "start-host",
      "role": "target",
      "command": {
        "name": "launch",
        "applicationId": "remoteassist-host"
      }
    },
    {
      "id": "host-window",
      "role": "target",
      "command": { "name": "inspect" },
      "waitFor": true,
      "commandTimeoutMilliseconds": 2000,
      "waitTimeoutMilliseconds": 30000,
      "pollMilliseconds": 500,
      "select": {
        "path": "/evidence/frames",
        "where": [
          {
            "path": "/window/pid",
            "op": "eq",
            "value": { "$ref": "/steps/start-host/value/pid" }
          },
          {
            "path": "/window/createdAt",
            "op": "eq",
            "value": { "$ref": "/steps/start-host/value/createdAt" }
          }
        ]
      },
      "expect": [
        {
          "path": "/window/imageHash",
          "op": "eq",
          "value": { "$ref": "/steps/start-host/value/imageHash" }
        }
      ]
    }
  ]
}
```

`preflight`의 각 필드는 다음 뜻이다.

| 필드 | 이 예에서 수행할 검사 |
|---|---|
| `timeoutSeconds: 20` | 모든 역할의 준비 검사를 합쳐 최대 20초 안에 끝낸다. 이 시간도 전체 120초에 포함한다 |
| `evidenceMaxAgeSeconds: 10` | 수행한 준비 검사의 결과 유효 기간이다. 10초가 지났으면 모드에 따라 재확인하거나 경고한다. 생략한 검사의 증거는 요구하지 않는다 |
| `roles.target.applications` | 대상 PC의 run 설정에서 `remoteassist-host`를 찾아 파일·해시·실행 허용 범위를 확인한다. 이 검사만으로 제품 앱을 실행하지 않는다 |
| `checks.user.mode: warn` | 실제 사용자 SID를 기대값과 비교한다. 다르거나 조회할 수 없으면 경고를 남기고 진행한다 |
| `checks.evidence-space` | Controller와 대상 PC의 결과 저장 볼륨에 각각 최소 256MiB가 남았는지 확인한다. 수집 계획의 예상량이 더 크면 그 값을 기준으로 삼는다. 부족하거나 조회할 수 없어도 이 예에서는 경고 후 진행한다 |
| `checks.recovery-probe.mode: skip` | 사전 복구 훈련을 실행하지 않는다. R1 복구 실측 증거도 요구하지 않는다. 실제 종료 시 입력 해제·소유 앱 종료는 수행한다 |

예상 디스크 여유를 확인하지 못해도 시험은 시작할 수 있다. 다만 실제 로그 저장 중 디스크가 가득 차면 그 저장 작업은 실패한다. 또한 디스크 여유 검사 생략과 Controller의 실행 보고서 저장 폴더 자체가 쓰기 불가능한 문제는 구분한다. 후자는 현재 파일 기반 실행기를 시작할 수 없는 실제 오류다.

PC마다 달라지는 값은 시나리오 대신 bindings와 run 설정에 둔다. 예를 들어 같은 폴더의 `lab.bindings.json`은 다음과 같다.

```json
{
  "parameters": {},
  "roles": { "target": "target.run.json" }
}
```

`target.run.json`의 관련 부분은 다음과 같다. **전체 run 파일이 아닌 발췌**이며, 기존 만료 시각·창 허용 범위·위임 설정 등도 필요하다. `expectedUserSid`는 G01에서 추가할 필드다. 실행 시 실제 로그인 사용자의 SID와 비교한다. 경로·SID·해시는 예시이므로 시험 환경의 실제 값으로 바꾼다.

```json
{
  "machineId": "lab-target-01",
  "role": "target",
  "targetSession": 1,
  "expectedUserSid": "<시험 사용자의 실제 Windows SID>",
  "expectedDesktop": "Default",
  "allowInput": true,
  "applications": [
    {
      "id": "remoteassist-host",
      "imagePath": "C:\\Lab\\RemoteAssist\\Host.exe",
      "imageHash": "<실행 파일의 실제 SHA-256 64자리>",
      "arguments": []
    }
  ]
}
```

이 설정을 읽은 도구는 다음 순서로 동작한다.

1. `target`을 `lab-target-01`에 연결하고 Client·Watchdog를 시작한다. 이 시점에는 제품 앱을 실행하거나 입력을 보내지 않는다.
2. 실행에 필요한 머신·세션·바탕화면·Client·Watchdog 상태·미완료 정리·`Host.exe`와 결과 저장 경로를 확인한다. 사용자 SID와 디스크 여유는 조회하되 불일치·조회 불가 시 경고만 남긴다. 별도 복구 훈련은 호출하지 않는다.
3. 실행 조건과 `required` 검사가 충족되면 이번 `executionId`·`runId`·설정 해시·시나리오 해시를 포함한 준비 결과를 저장한다. 경고·확인 불가·생략도 함께 기록한다. 이 식별값은 작성자가 시나리오에 직접 적지 않는다.
4. 준비 결과가 유효한 상태에서만 `start-host`를 실행한다. 이어서 `host-window`가 최대 30초 동안 해당 프로세스의 창 하나를 기다린다. 여러 창이 조건에 맞으면 모호한 대상으로 실패하므로, 실제 제품이 여러 창을 띄우면 제목 등 추가 선택 조건을 둔다. 다른 프로세스에 UI를 띄우는 제품은 그 프로세스도 별도 등록·확인해야 한다.
5. 예를 들어 사용자 SID가 기대값과 달라도 이 예의 `user` 모드는 `warn`이므로 경고 후 `start-host`를 실행한다. 반드시 해당 사용자여야 하는 시험이면 `user.mode`를 `required`로 바꾼다. 그때는 불일치·조회 불가 시 본 시험 단계를 `NotRun`으로 기록하고 Client·Watchdog를 정리한다.

두 PC를 사용하는 시험은 `roles`에 `supporter`를 추가하고, `preflight.roles.supporter`에 지원자 앱과 검사 모드를 선언하며, bindings에 지원자 run 파일을 연결한다. **모든 PC의 실행 조건과 `required` 검사가 충족되면 시작한다. `warn`·`skip` 항목 때문에 전체 시험을 차단하지 않는다.**

## G02. 시나리오에서 별도 프로그램에 작업을 요청하고 결과 받기

**문제:** 앱마다 확인해야 할 정보가 다르다. 예를 들어 어떤 앱은 화면의 글자를 읽어야 하고, 어떤 앱은 Windows 서비스가 실행 중인지 확인해야 한다. 현재 시나리오는 정해진 앱 조작 명령을 사용한다. 별도 프로그램에 그때 필요한 값을 넘겨 작업을 요청하고, 응답을 다음 단계에 사용하는 기능은 부족하다.

**만들 기능:** 별도 프로그램을 설정에 등록하고 시나리오에서 호출하는 방법을 만든다. 등록할 때 프로그램의 위치, 요청할 수 있는 작업, 전달할 값, 돌려받을 결과, 실행 시간 제한을 정한다.

예를 들면 다음과 같다. 아래는 추가할 기능의 사용 예다.

1. 사용하는 프로젝트에서 서비스 상태를 확인하는 작은 프로그램을 준비한다.
2. 이 프로그램을 DesktopTestDriver 설정에 등록한다.
3. 시나리오가 프로그램에 서비스 이름을 전달하며 실행 상태를 물어본다.
4. 프로그램이 “실행 중” 또는 “중지됨”을 반환한다.
5. 시나리오가 “실행 중”인지 확인하고, 맞으면 다음 단계로 진행한다.

**좋아지는 점:** 새로운 제품을 시험할 때 필요한 확인 기능을 별도 프로그램으로 추가할 수 있다. Controller·Agent 코드를 제품마다 수정하지 않고 시나리오와 설정으로 연결할 수 있다.

### 구현 방법

1. **실행 가능한 프로그램을 run 설정에 등록한다.** `RunConfig`에 프로그램 ID, 절대 경로, SHA-256, 허용 작업 목록, 요청·응답의 JSON 형식, 호출 시간·출력 크기 제한을 추가한다. 각 작업에는 읽기 전용인지 상태를 변경하는지도 선언한다. 시나리오는 등록 ID와 작업 이름만 지정한다.
2. **`invoke-helper` 명령을 추가한다.** `ScriptCommands`에서 문법과 허용 범위를 검사하고, `Command`와 `CommandEngine`을 통해 해당 역할의 PC에서 실행한다. `ProcessStartInfo`의 셸 실행을 끄고 JSON 요청을 표준 입력으로 전달한다. 프로그램 경로·셸 명령을 시나리오에서 임의로 조립하지 않는다. 기존 `ExternalFixtureBackend`·`ExternalConsoleAdapter`의 프로세스 통신 방식을 공통 실행기로 추출한다.
3. **요청과 응답을 정확히 대응시킨다.** 요청에는 프로토콜 버전, `executionId`, `runId`, `requestId`, 작업명, 인자를 넣는다. 응답에는 같은 식별자, 관측 시각, 작업 성공 여부, 결과값, 오류를 요구한다. 식별자·형식 불일치, 비정상 종료, 제한 시간 초과는 명령 실패다. 시간 초과 시 해당 호출의 자식 프로세스까지 종료하고 표준 오류도 크기를 제한해 기록한다.
4. **반환값을 기존 조건식과 연결한다.** 정상 응답의 결과 객체를 단계의 `value`로 제공한다. 기존 `expect`로 검사하고 `$ref`로 다음 단계에 전달한다. 읽기 전용 작업만 G07의 반복 관측을 허용한다. 서비스 중지·설치처럼 상태를 바꾸는 호출은 자동 재실행하지 않고 G04의 복구 작업을 함께 등록한다.

예를 들어 다음은 **추가할 명령의 단계 예시**다. `service-check` 프로그램과 `query-service` 작업이 대상 PC의 run 설정에 등록되어 있다고 가정한다.

```json
{
  "id": "service-running",
  "role": "target",
  "command": {
    "name": "invoke-helper",
    "helperId": "service-check",
    "operation": "query-service",
    "arguments": { "serviceName": "ProductService" }
  },
  "expect": [{ "path": "/state", "op": "eq", "value": "Running" }]
}
```

프로그램 실행 자체가 성공해도 반환값이 `{"state":"Stopped"}`면 위 단계는 실패다. 서비스 이름과 기대 상태는 사용하는 프로젝트가 정하고, DesktopTestDriver는 호출·형식 검사·판정만 담당한다.

**완료 기준:** 정상 반환값의 조건 검사와 다음 단계 참조가 가능해야 한다. 미등록 작업, 잘못된 응답, 다른 실행의 응답, 무응답 프로그램은 실패해야 하며, 남은 자식 프로세스가 없어야 한다.

## G03. 시험 도구가 보낸 입력과 제품이 보낸 입력 구분

**문제:** 원격 제어 제품을 시험할 때는 제품이 대상 PC에 입력을 보내야 한다. 그런데 현재 입력 감시는 다른 프로그램이 보낸 입력을 충돌로 판단해 시험을 중단할 수 있다. 반대로 시험 도구가 대상 PC에 직접 문자를 넣으면, 제품의 원격 입력이 성공한 것처럼 잘못 판정할 수 있다.

**만들 기능:** 준비 단계에서는 Agent가 앱을 조작하고, 원격 입력을 확인하는 단계에서는 대상 PC의 Agent가 입력을 멈추고 결과만 읽도록 전환한다. 클릭 횟수·입력된 문자·눌린 키 상태를 표시하는 시험용 창도 시나리오에서 실행하고 읽을 수 있게 연결한다. 관련 기능 일부는 기존 코드에 있지만 현재 시나리오에서는 호출할 수 없다.

**좋아지는 점:** “지원자 PC에서 조작한 내용이 제품을 거쳐 대상 PC에 도착했는가”를 확인할 수 있다. 시험 도구가 대신 입력한 결과와 구분할 수 있다.

### 구현 방법

1. **이미 있는 명령을 시나리오에 노출한다.** `CommandEngine`의 `fixture-start`, `fixture-observe`, `seal-input`, `resume-input`을 `ScriptCommands`의 필드·허용 권한·읽기/변경 분류에 추가한다. `fixture-start`는 등록된 `FixtureScope`만 실행하고, `seal-input`은 현재 시나리오 ID를 위임 범위와 대조한다.
2. **대상 PC의 입력을 끊은 뒤 기준값을 잡는다.** 먼저 `fixtures/MarkerWindow`를 실행하고 필요한 위치와 포커스를 준비한다. `seal-input`으로 Agent가 누른 키·버튼을 해제한 뒤 입력을 금지한다. 이후 `fixture-observe`로 클릭 횟수·문자·이벤트 순번을 읽어 기준값으로 저장한다. 봉인 뒤에는 포커스 변경과 앱 실행을 포함한 직접 조작도 거부한다.
3. **지원자 PC에서만 시험 입력을 보낸다.** 이번 실행에서 만든 고유 문자열과 정해진 클릭·키 누름/해제를 원격 제품 화면에 전달한다. 대상 PC는 읽기 명령만 사용해 기준값 이후 클릭 증가량, 문자열 일치, 키 해제 여부를 확인한다. 관측 결과의 `runId`, 시험 창의 프로세스 식별, 신선도·이벤트 누락 여부는 기존 `OwnedFixture.Observe` 검사로 검증한다.
4. **입력 감시를 무조건 해제하지 않는다.** 기존 `InputConflictPolicy`는 입력 봉인과 제품 `control` 권한이 있을 때 외부 프로그램의 주입 입력을 허용한다. 이 동작을 유지하고 실제 키보드·마우스 입력은 충돌로 처리한다. `resume-input`은 제품 입력 시험이 끝났다는 기록을 남긴 뒤 준비·정리 단계에서만 허용한다.

이 방식은 **Agent가 대신 입력하지 않았음**을 보장하는 설계다. Windows 입력 플래그만으로 어느 제품이 입력했는지까지 식별하지는 못한다. 따라서 전용 시험 세션에서 다른 입력 프로그램을 배제하고, 고유 문자열과 제품 연결 기록을 함께 확인한다. 제품이 가상 HID 등으로 입력해 물리 입력처럼 보이는 경우는 현 감시 정책에서 충돌하므로, 장치별 식별 수단을 추가하기 전에는 해당 입력 경로를 미지원으로 보고한다.

**완료 기준:** 봉인 후 대상 Agent의 문자 입력·클릭·포커스 변경이 거부되어야 한다. 지원자에서 보낸 고유 문자열과 클릭은 대상 시험 창에서 확인되고, 실제 사용자 입력·관측 누락은 시험 실패로 기록되어야 한다.

## G04. 실패하더라도 제품 종료와 원상 복구 수행

**문제:** 현재는 실패하면 남은 시나리오 단계를 건너뛰고 Agent 작업을 종료한다. 따라서 뒤에 적어 둔 “제품 연결 종료”나 “변경한 서비스 복원” 단계가 실행되지 않을 수 있다. 시험 도구가 종료됐다는 사실만으로 제품도 정리됐다고 볼 수 없다.

**만들 기능:** 성공·실패와 관계없이 마지막에 실행할 정리 단계를 따로 적을 수 있게 한다. 입력 중지, 제품 연결 종료, 결과 저장, 시험 중 실행한 앱 종료, 변경한 설정 복원을 순서대로 수행한다. 정리에 실패한 기록은 프로그램을 다시 실행해도 남겨 두고, 해결 전에는 다음 시험을 차단한다.

**좋아지는 점:** 중간에 실패해도 제품 연결이나 시험 앱이 남아 사용자의 작업을 방해하는 일을 줄인다. 정리가 어디까지 끝났는지도 확인할 수 있다.

### 구현 방법

1. **본 시험과 정리 절차를 별도 배열로 선언한다.** `ScriptScenario`에 `cleanup`과 정리 시간 예산을 추가한다. `ScriptScenarioRunner`는 본 시험의 성공·오류·취소 모두에서 `finally`로 정리 절차에 진입한다. 현재도 수행하는 역할별 `end`는 최종 안전 정리로 유지한다. 정리 단계는 시작되지 않았거나 준비가 덜 된 역할에서도 안전하게 건너뛰거나 이미 정리된 상태로 완료될 수 있어야 한다.
2. **일반 명령이 막힌 뒤의 실행 경로를 만든다.** 현재 `CommandEngine`은 명령 오류 시 `store.Stop`을 기록하고 입력·소유 프로세스 정리를 시도한다. 따라서 `finally`에서 기존 UI 명령을 다시 보내는 것만으로 제품 연결을 종료할 수 없다. 실패 즉시 일반 입력을 중지하고, 정리 작업은 상시 `PersistentAgent` 또는 독립 복구 프로그램에서 실행한다. 이 경로는 사전에 등록한 연결 종료·자원 복원 작업만 허용하고 일반 입력 허용을 되살리지 않는다.
3. **정리 순서와 실패 시 진행 규칙을 정한다.** 입력 중지·눌린 키 해제 → 제품 연결 종료 → 남아 있는 화면·로그 수집 → 소유 시험 앱 종료 → 서비스·설정 복원 → 최종 상태 확인 순으로 수행한다. 화면 수집에는 G06의 제한 시간을 두고, 수집 실패가 자원 복원을 막지 않게 한다. 오류 때문에 앱이 먼저 종료됐다면 화면 부재를 기록하고 나머지 정리를 계속한다. 한 정리 작업이 실패해도 독립적인 후속 작업과 다른 PC의 정리는 수행한다.
4. **변경하기 전에 복구 기록을 저장한다.** 서비스 변경 등에는 원래 값, 대상 자원, 수행할 복원 작업을 영속 파일에 먼저 기록한다. 각 작업의 상태를 `pending`·`running`·`verified`·`failed`로 저장한다. 중간에 프로세스가 죽으면 결과 미확정으로 남기고, 재시작 시 실제 상태를 읽어 복원한다. 이미 복원된 자원에 다시 실행해도 같은 결과가 되도록 작업을 설계한다.
5. **정리 완료를 확인한 뒤 다음 시험을 허용한다.** `PersistentAgent` 시작 시 미완료 기록을 검사해 `CleanupBlocked`를 복원한다. Controller도 연결이 끊긴 PC를 정리 완료로 간주하지 않는다. 제품 세션 종료, 소유 프로세스 부재, 입력 해제, 원래 설정 복원, 일반 바탕화면 복귀를 확인해야 차단을 해제한다. 기록 삭제만으로 해제하지 않는다.
6. **시험 실패와 정리 실패를 따로 보고한다.** `ScriptReport`에 최초 실패 단계·오류와 정리 단계별 결과를 각각 남긴다. 정리가 성공해도 본 시험 실패를 통과로 바꾸지 않는다. 정리 미완료 시 최종 오류는 `CleanupIncomplete`로 표시하되 최초 실패 원인도 보존한다.

**완료 기준:** 입력 직후 오류, 명령 시간 초과, 사용자 취소, Client 강제 종료, Controller·Agent 재시작을 각각 시험한다. 복원 가능한 경우에는 원래 상태로 돌아오고, 복원을 확인하지 못한 PC에서는 다음 시험이 차단되어야 한다.

## G05. 화면에 실제로 나타난 결과 읽기

**문제:** 클릭 명령이 성공해도 앱이 의도대로 동작했는지는 별도로 확인해야 한다. 현재는 창과 버튼의 일부 정보를 읽을 수 있지만, 입력란에 실제로 적힌 문자나 브라우저의 연결 상태·재생 영상을 확인하는 기능은 부족하다.

**만들 기능:** 일반 앱의 입력값과 브라우저 화면의 필요한 정보를 읽는 방법을 추가한다. 예를 들어 “연결됨” 문구, 입력란의 문자, 영상이 표시되고 바뀌는지를 확인할 수 있어야 한다. 영상에는 이번 시험에서만 표시한 번호나 그림을 사용해 예전 화면과 구분한다. 제품마다 다른 화면 위치와 기대 결과는 시나리오에 적는다. 별도 확인 프로그램이 필요한 경우 G02로 연결한다.

**좋아지는 점:** “클릭을 보냈다”에서 끝나지 않고 “앱에 원하는 결과가 나타났다”까지 자동으로 판정할 수 있다.

### 구현 방법

1. **일반 앱은 Windows UI Automation부터 확장한다.** 현재 `UiNode`에는 이름·AutomationId·종류·영역·활성 상태·토글 값이 있다. `WindowsDesktop.ReadControls`에서 `ValuePattern`·`TextPattern`을 지원하는 요소의 실제 값과 읽기 지원 여부를 추가로 반환한다. 값을 읽을 수 없는 경우와 빈 문자열을 구분하고, 암호 필드는 반환하지 않는다. UIA 호출은 별도 작업 프로세스에 격리해 앱 응답 중지 시에도 제한 시간에 종료할 수 있게 한다.
2. **브라우저의 구조화된 정보는 G02로 읽는다.** 프로젝트가 제공하는 브라우저 확인 프로그램이 해당 시험에서 실행한 브라우저의 자동화 연결을 사용해 URL·요소 텍스트·입력값·연결 상태를 반환한다. 셀렉터와 기대값은 프로젝트 설정에 둔다. 자동화 연결을 제공하지 않는 화면은 UIA 또는 영역을 제한한 OCR 확인 프로그램을 사용한다. 요소가 여러 개이거나 판독이 불확실하면 결과를 미확정으로 돌려준다.
3. **영상은 이번 실행의 내용과 갱신 여부를 함께 확인한다.** 기존 `VisualMarker.Colors(runId)`는 실행마다 다른 정적 색 띠를 만든다. `MarkerWindow`에 증가하는 화면 번호와 Controller가 발급한 새 확인값을 표시하는 기능을 추가한다. 확인값은 해당 시험 창에만 연결되는 전용 제어 메시지로 전달하고, 화면 번호는 창이 스스로 증가시킨다. 이 경로는 키보드·마우스 입력을 만들지 않아 G03의 입력 봉인 후에도 사용할 수 있다. 지원자 화면의 영상 영역에서 대상 PC의 색 띠·확인값을 찾고, 이후 화면 번호가 증가하는지도 판독한다. 정지된 옛 화면이나 로딩 애니메이션만으로 통과하지 않게 한다.
4. **관측 범위와 결과를 명시한다.** 각 읽기는 창 식별값, UIA ID·브라우저 셀렉터·영상 영역 중 하나를 대상으로 한다. 결과에는 읽은 값, 읽기 방법, 관측 시각, 근거 화면 ID를 포함한다. Controller가 기존 `expect`로 비교하고 G07로 완료를 기다린다. 관측을 위해 Agent가 포커스를 바꾸거나 입력을 보내지 않는다. 현재 전경 창을 요구하는 `snapshot`은 별도 관측용 캡처와 구분해, 필요한 창이 보이지 않는 경우 관측 불가를 반환하도록 확장한다.

예를 들어 원격 문자 시험은 지원자에서 `이번 실행의 고유 문자열`을 입력하고, 대상 시험 창의 실제 문자열이 같은지 비교한다. 영상 시험은 대상에 새 확인값을 표시한 **후** 지원자 영상에서 같은 값과 증가한 화면 번호를 읽어야 통과한다. 두 시험의 근거는 각각 대상 입력 결과와 지원자 캡처다.

**완료 기준:** UIA 입력값·브라우저 상태·정상 갱신 영상은 판정할 수 있어야 한다. 값 읽기 미지원, 다른 실행의 영상, 정지 영상, 모호한 요소·판독은 통과하지 않아야 한다.

## G06. 이번 시험의 화면과 결과를 한곳에 저장

**문제:** 현재 화면을 캡처해도 이미지가 시험 PC에 남고, 시나리오 결과 폴더로 자동 수집되지 않는다. 결과 파일을 읽는 기능도 있지만 그 파일이 이번 시험에서 만들어졌는지는 별도로 확인해야 한다. 이전 시험의 성공 파일을 읽으면 잘못 통과할 수 있다.

**만들 기능:** 시험 앱을 종료하기 전에 화면 이미지와 필요한 기록을 조작 PC로 모은다. 시험 번호·PC·단계·생성 시각을 함께 저장하고, 이전 시험의 파일은 결과로 인정하지 않는다.

**좋아지는 점:** 조작 PC의 결과 폴더만 열어도 무엇을 실행했고, 어느 화면에서 실패했고, 정리가 끝났는지 확인할 수 있다. 오래된 결과 때문에 잘못 통과하는 일도 막는다.

### 구현 방법

1. **현재 결과 폴더에 실제 파일을 수집한다.** `ScriptScenarioRunner`가 만드는 `scenarios/<executionId>/` 아래 역할·단계별 폴더를 추가한다. 기존 `plan.json`, `execution.json`, `events.jsonl`, `report.json`과 함께 PNG, 결과 JSON, 필요한 로그를 저장한다. `report.json`에는 각 근거 파일의 상대 경로를 넣는다.
2. **기존 이미지 분할 읽기를 연결한다.** `CommandEngine.ReadFrame`은 이미 이미지의 일부를 Base64와 오프셋·전체 크기·SHA-256으로 반환한다. Controller 수집기를 추가해 캡처의 `frameId`로 파일을 나눠 받고, 임시 파일에 기록한 뒤 전체 크기·SHA-256을 확인해 최종 이름으로 바꾼다. 일반 결과 파일도 등록된 파일 ID로만 읽는 같은 방식을 추가한다. 원격 PC의 임의 경로를 그대로 요청하지 않는다.
3. **파일의 생성 경위를 검증한다.** 수집 목록에는 `executionId`, `runId`, 머신·역할·단계 ID, 요청 ID, 생성 시각, 바이트 수, SHA-256을 기록한다. 제품 확인 프로그램은 이번 실행 전용 폴더에 결과를 만들고 요청 ID를 응답에 포함한다. `read-artifact`는 내용 해시만 읽는 현재 방식에 실행 식별 검사를 추가한다. 수정 시각이 최근이라는 조건만으로는 이번 결과로 인정하지 않는다. 원본에 실행 ID를 넣을 수 없다면 G02 확인 프로그램이 이번 요청으로 새 결과를 생성하거나, 시험 시작 때 저장한 이벤트 순번·로그 위치 이후의 결과만 추출하게 한다. 기존 성공 파일을 읽어 새 요청 ID로 감싸는 것만으로는 생성 경위를 증명할 수 없으므로, 이런 파일은 참고 자료로만 수집한다.
4. **실패 후에도 수집할 통로를 남긴다.** 정상 수집은 앱 종료 전에 수행한다. Client가 멈춘 경우에는 `PersistentAgent`가 run의 수집 목록에 고정된 기존 파일만 읽어 전송하게 한다. 중지 플래그를 지우거나 입력 권한을 다시 열지 않는다. Client 종료 후 새 화면을 얻을 수 없으면 마지막 캡처와 로그를 수집하고 누락을 표시한다.
5. **실패·용량 초과를 결과에 남긴다.** 파일별·전체 용량과 수집 시간에 상한을 두고 기존 `EvidencePolicy`와 함께 검사한다. 크기·해시 불일치와 전송 중단 파일은 미완료로 표시한다. 필수 근거가 없으면 시험을 통과시키지 않는다. 수집에 실패해도 G04의 앱 종료·복원을 계속한다.

**완료 기준:** 두 PC의 근거를 Controller 결과 폴더만으로 열 수 있어야 한다. 이전 실행의 성공 파일, 손상 파일, 중간에 끊긴 이미지, 용량 초과 결과는 검출되고 보고서에 누락 이유가 남아야 한다.

## G07. 여러 PC의 준비가 끝날 때까지 기다리기

**문제:** 현재 시나리오의 한 단계는 최대 5초다. 앱 실행이나 연결 준비가 그보다 오래 걸리면 정상적으로 진행 중이어도 실패할 수 있다. 여러 PC가 모두 준비된 뒤 다음 동작을 시작하는 기능도 부족하다.

**만들 기능:** 개별 명령을 실행하는 시간과 준비 완료를 기다리는 시간을 나눠 지정하게 한다. “대상 PC의 시험 창이 준비됐다”, “지원자 PC에 영상이 표시됐다” 같은 조건을 확인한 뒤 다음 단계로 넘어간다. 기다리는 시간도 시험 전체 시간 제한에 포함한다.

**좋아지는 점:** 빠른 PC와 느린 PC에서 같은 시나리오를 사용할 수 있다. 준비 전에 클릭하거나, 무조건 몇 초씩 기다리는 방식의 실패를 줄인다.

### 구현 방법

1. **명령 1회의 시간과 조건 대기 시간을 분리한다.** 버전 2 단계에는 `commandTimeoutMilliseconds`와 `waitTimeoutMilliseconds`를 둔다. 예를 들어 1회의 상태 조회는 2초, 준비 대기는 60초, 관측 간격은 500ms로 설정한다. Agent 명령은 기존 5초 상한 안에서 짧게 끝내고, 긴 대기는 Controller가 여러 번 조회해 구현한다. 버전 1의 `timeoutMilliseconds` 의미는 유지한다.
2. **재조회 가능한 결과를 구분한다.** 창이 아직 없거나 준비 조건이 거짓인 정상 응답은 다시 조회한다. 생성 예정 파일은 명시적으로 등록한 대기 작업에서만 `pending`으로 반환한다. 권한 오류, JSON 손상, 대상 변경, 연결 끊김은 즉시 실패다. `inspect`·`controls`·`read-artifact`와 새 읽기 명령, G02에서 읽기 전용으로 등록한 작업만 반복한다. 클릭·앱 실행·서비스 변경은 반복하지 않는다.
3. **여러 역할의 조건을 한 단계에서 확인한다.** `barrier` 단계에 역할별 읽기 명령과 기대 조건을 배열로 선언한다. 예를 들어 대상의 시험 창 준비와 지원자의 연결 상태를 함께 검사한다. 각 역할은 동시에 관측하되 같은 Agent의 명령은 직렬 처리한다. 모든 조건이 충족되고 마지막 관측이 정해진 유효 시간 안에 있어야 다음 단계로 진행한다. 먼저 준비된 PC의 상태도 기다리는 동안 다시 읽어, 중간에 창이 사라진 것을 놓치지 않는다.
4. **모든 대기에 공통 마감 시각을 적용한다.** 실제 허용 시간은 명령 제한, 단계 대기 잔여 시간, 전체 시험에서 정리 시간을 뺀 잔여 시간 중 가장 짧은 값이다. 경과 시간은 단조 시계로 계산하고, heartbeat와 취소 처리는 대기 루프와 독립적으로 유지한다. 1,024회 명령 제한 등 기존 횟수·로그 예산도 함께 검사해 실행 전에 부족한 설정을 거부한다.
5. **기존 동기화 코드를 보완해 재사용한다.** `Campaign.Barrier`에는 이미 여러 PC의 결과를 모으는 코드가 있지만 5초 제한과 별도 실행 경로를 사용한다. 역할별 조건 반복 조회·관측 유효 기간 검사를 공통화하고 `ScriptScenarioRunner`에 연결한다. 대기 실패 보고서에는 준비되지 않은 역할, 마지막 관측값, 기대값, 시도 횟수와 경과 시간을 남긴다.

**완료 기준:** 한 PC가 30초 뒤 준비되어도 지정 시간 안이면 통과해야 한다. 끝내 준비되지 않는 PC, 준비 후 다시 사라진 창, 대기 중 단절은 실패해야 한다. 취소·전체 시간 초과 시에는 대기를 종료하고 확보한 정리 시간으로 복구해야 한다.

## 관리자 화면·설치·장시간 시험에 필요한 추가 기능

제품의 해당 기능까지 시험하려면 다음 작업도 필요하다.

| 시험할 내용 | 현재 문제 | 만들어야 할 기능과 효과 |
|---|---|---|
| 관리자 승인 화면·잠금 화면 | 현재 Agent는 로그인한 사용자의 일반 바탕화면을 대상으로 한다 | 해당 화면을 조작·확인하고 일반 화면으로 복귀하는 별도 실행 수단을 연결한다. 관리자 화면 지원 여부를 실제로 시험할 수 있다 |
| 서비스 장애·설치·업데이트 실패 | 일반 앱을 닫는 것만으로 서비스와 설치 상태를 복구할 수 없다 | 대상 서비스·설치를 조작하는 별도 프로그램과 복구 절차를 G02·G04에 연결한다. 실패를 발생시킨 뒤 원래 상태로 돌아왔는지 확인할 수 있다 |
| 장시간 실행 | 현재 기본 시나리오는 최대 15분이다 | 장시간 실행을 감독하고 성능 기록과 종료·정리를 관리하는 별도 실행 기능을 만든다. 오랫동안 실행할 때만 발생하는 문제를 확인할 수 있다 |

### 관리자 승인 화면·잠금 화면 구현

일반 바탕화면용 Agent의 입력 권한을 높이는 방식으로 처리하지 않는다. 현재 `WindowsDesktop`·`RunConfig`는 `Default` 바탕화면을 전제로 하므로, VM 콘솔이나 하드웨어 KVM을 별도 제어 수단으로 연결한다.

1. `secure-desktop.json`의 UAC·잠금·SAS 작업 정의와 `ExternalConsoleAdapter`·`ExternalFixtureBackend`를 연결한다. 기존 콘솔 어댑터는 `probe`·`recover`만 제공하므로, 화면 관측·콘솔 입력은 별도 작업 계약으로 추가한다.
2. 시작 전에 독립 복구 가능 여부를 확인하고 `RecoveryGrade.R2`를 요구한다. 일반 Agent가 아닌 콘솔 경로에서 화면을 확인하고 필요한 조작을 수행한다. 제품의 관리자 화면 전송·원격 입력 성공은 지원자 화면과 대상 콘솔 상태를 함께 비교한다.
3. 시험 종료 시 일반 바탕화면과 원래 사용자 세션으로 돌아왔는지 확인한다. 실패하면 독립 복구 경로를 실행하고, 복귀 미확인 상태에서는 G04에 따라 다음 시험을 차단한다.

**완료 기준:** 전용 VM에서 UAC·잠금 화면 진입, 제품을 통한 관측·입력 확인, 일반 화면 복귀를 검증한다. 복구 경로가 없으면 실행 전에 미지원으로 차단해야 한다.

### 서비스 장애·설치·업데이트 실패 구현

제품별 작업은 G02의 별도 프로그램에 구현하고, Controller에는 공통 요청·결과·복구 처리만 둔다. `fixtures/service-failure.json`·`fixtures/install-update-rollback.json`과 `Fixtures.cs`의 작업·복원 정의를 재사용한다.

1. 변경 전 서비스 상태·시작 유형, 설치 버전·패키지 해시, 필요한 설정을 기록하고 복원 방법을 확정한다. 스냅샷 복구가 필요한 시험은 전용 VM과 R2 복구를 요구한다.
2. 필요한 권한을 가진 전용 실행기가 등록된 서비스·패키지만 대상으로 중지·장애 주입·설치·업데이트를 수행한다. 설치 프로세스의 종료 코드만 보지 않고 실제 설치 버전·서비스 상태·앱 실행 결과를 확인한다.
3. 성공·실패 모두에서 G04의 복원 절차를 수행하고 최초 기록과 비교한다. 재부팅이 필요한 경우 같은 실행의 복구 기록을 재시작 후 읽어 이어가며, 확인 전에는 새 시험을 받지 않는다. 현재 단발성 외부 프로그램 호출만으로는 재부팅을 넘길 수 없으므로 이 감독 기능도 추가한다.

**완료 기준:** 서비스 중지와 업데이트 중 실패를 각각 발생시킨 뒤 원래 버전·설정·서비스 상태로 돌아와야 한다. 복원 실패와 재부팅 후 복원 미완료 상태는 다음 시험을 차단해야 한다.

### 장시간 실행 구현

단계의 제한 시간을 수 시간으로 늘리지 않고 별도 감독 실행 모드를 만든다. 현재 `ScriptScenario`·`RunConfig`는 최대 900초이고, `FixtureRunner`의 별도 경로는 최대 7,800초까지 허용한다. 후자를 그대로 연결하는 것만으로 시간 단위·밤샘 시험 전체가 완성되지는 않는다.

1. 감독 계획에 전체 시간, 성능 수집 주기, 이상 판정 조건, 정리 예산을 둔다. 시작 전에 `RunConfig`의 유효 기간·최대 시간, 위임 범위, Watchdog와 외부 실행기의 수명 제한을 함께 확장·검사한다. 한 파일의 15분 상한만 바꾸지 않는다.
2. 제품 연결과 부하는 유지한 채 짧은 관측 작업을 주기적으로 실행한다. CPU·메모리·핸들 수·연결 상태·영상 갱신을 시간 순서로 수집한다. 제품을 매 주기 재시작하면 누적 문제를 가리므로, 재시작 여부는 시험 계획에 명시한다.
3. 실행 시작 시각·누적 경과 시간·마지막 수집 결과·소유 자원·복구 절차를 디스크에 기록한다. 감독 프로세스가 재시작되면 남은 자원을 확인해 정리하고 실행은 중단으로 보고한다. 자동으로 성공 처리하거나 본 시험을 재실행하지 않는다.
4. 로그·이미지는 용량을 제한해 순환 저장하고, 이상 발생 전후 기록을 별도로 보존한다. 취소·시간 종료·제품 응답 중지 시에는 입력을 멈추고 G06 수집과 G04 복원을 수행한다.

**완료 기준:** 지정한 장시간 동안 연결과 관측이 유지되고, 자원 증가가 기록되어야 한다. 정상 종료·중간 취소·감독 프로세스 종료 후 모두 정리 여부를 확인할 수 있어야 한다. 가짜 시간 기반 검사와 실제 시간 동안 수행한 시험은 보고서에서 구분한다.

## RemoteAssist에 적용하면 어떻게 되는가

| 시험 순서 | 필요한 보완 |
|---|---|
| 대상 PC와 지원자 PC의 앱을 준비한다 | G01: 실제 시험을 시작할 수 있는 상태인지 확인 |
| 접속 정보를 입력하고 대상자 동의를 거친다 | G05: 화면에서 필요한 값을 읽고 결과 확인 |
| 대상 PC의 Agent는 직접 입력을 멈춘다 | G03: 제품이 보낸 입력만 확인하도록 전환 |
| 지원자 PC에 대상 화면이 보이는지 확인한다 | G05·G07: 이번 시험 화면이 표시될 때까지 기다리고 확인 |
| 지원자 PC에서 클릭·문자를 보낸다 | 기존 입력 기능 사용 |
| 대상 PC의 시험용 창에서 반영 결과를 읽는다 | G03·G05: 클릭 횟수·문자·키 상태 확인 |
| 제품 연결을 종료한다 | G04: 중간에 실패했어도 종료 수행 |
| 화면과 결과 기록을 저장한다 | G06: 시험 앱 종료 전에 수집 |
| 시험 중 실행한 앱을 닫고 정리 결과를 확인한다 | G04: 다음 시험을 시작할 수 있는 상태인지 확인 |

이때 RemoteAssist의 화면 이름·버튼·기대 결과는 사용하는 프로젝트의 시나리오에 둔다. 추가 확인 프로그램도 해당 프로젝트가 제공하고 G02로 연결한다. DesktopTestDriver에는 공통 실행 기능을 한 번 개발해 여러 제품에서 재사용한다.

구현 후의 데이터 흐름은 다음과 같다. 아래는 실행 가능한 JSON이 아닌 절차 설명이다.

```text
Controller: executionId 발급 → 모든 역할 begin → G01 준비 검사
대상 PC:   제품·시험 창 준비 → 입력 봉인 → 클릭·문자 기준값 관측
지원자 PC: 제품 연결 → 대상의 새 화면 확인값·화면 번호 갱신 확인
지원자 PC: 고유 문자열 입력·클릭 → 대상 PC: 결과를 읽기만 수행
Controller: 대상 관측값을 기대값과 비교 → 본 시험 결과 확정
항상 수행: 입력 중지 → 제품 연결 종료 → 근거 수집 → 앱 종료·원상 복구
Controller: 본 시험 결과와 정리 결과를 함께 저장 → 미정리 PC 차단
```

## 개발 순서

1. **이미 있는 기본 기능부터 실행 검증한다.** 두 PC에서 앱 실행·입력·결과 확인·종료가 실제로 동작하는지 확인한다.
2. **G01·G03·G04·G06을 보완한다.** 준비 확인, 입력 구분, 실패 정리, 결과 저장을 먼저 갖춘다.
3. **G02를 만들고 G05·G07에 연결한다.** 제품별 확인 프로그램을 연결하고, 실제 결과를 기다려 판정하게 한다.
4. **사용하는 프로젝트의 시나리오로 검증한다.** RemoteAssist를 포함한 제품별 시험은 각 프로젝트에서 작성한다.

구현 시에는 다음 단위로 나눠 검토·검증한다. G04·G06에서 사용하는 공통 외부 프로그램 실행기는 G02의 전체 시나리오 문법보다 먼저 만들 수 있다.

| 구현 단위 | 주로 수정할 코드 | 해당 단계에서 확인할 결과 |
|---|---|---|
| 현재 기능의 기준 실행 | 기존 시나리오와 두 PC 시험 환경 | 앱 실행·입력·관측·종료의 실제 결과와 현재 실패 지점 |
| 버전 2 계약과 준비 검사 | `ScriptScenario.cs`, `Protocol.cs`, `Preparation.cs`, `ScriptScenarioRunner.cs` | 버전 1 호환, 검사별 차단·경고·생략, 실행 조건과 필수 검사 충족 전 조작 차단 |
| 입력 분리 | `ScriptScenario.cs`, `CommandEngine.cs`, `DesktopFixture.cs`, `WindowsDesktop.cs` | 대상 직접 입력 차단과 지원자 원격 입력 결과 확인 |
| 실패 복구·수집 | `ScriptScenarioRunner.cs`, `PersistentAgent.cs`, `RunStore.cs`, `CommandEngine.cs`, 공통 외부 프로그램 실행기 | 명령 실패·프로세스 종료 후 근거 보존, 원상 복구, 미완료 차단 |
| 제품별 확장·실제 결과 판정 | 외부 프로그램 실행기, `ScriptScenario.cs`, `Protocol.cs`, `WindowsDesktop.cs`, `MarkerWindow` | 별도 프로그램 결과 참조, UIA 값·현재 영상 판정 |
| 조건 대기·여러 PC 동기화 | `ScriptScenarioRunner.cs`, `Campaign.cs` | 느린 PC 대기, 준비 상태 재확인, 전체 시간·정리 예산 준수 |
| 관리자·설치·장시간 확장 | `Fixtures.cs`, 외부 어댑터, 별도 감독 실행기 | 독립 복구와 재시작 후 정리, 장시간 관측의 실제 실행 증거 |

계약·시간 제한·오류·복구 상태 전이는 `tests/Driver.Tests`에서 가짜 Agent와 제어 가능한 시간으로 검증한다. 실제 입력 감시, UIA, 영상, 관리자 화면, 설치 복구는 두 PC 또는 전용 VM에서 별도로 검증한다. 자동 검사 통과와 실제 제품 시험 통과를 같은 의미로 보고하지 않는다.

이 문서는 2026-10-20 기준 코드 검토로 정리한 추가 개발 항목이다. 기능 구현과 실제 실행 검증은 별도 작업이다.
