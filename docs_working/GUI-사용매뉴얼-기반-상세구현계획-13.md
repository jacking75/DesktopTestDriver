## 1. 이 문서의 목적과 기준

이 문서는 [간단한 GUI 테스트 사용 매뉴얼 11번](간단한-GUI-테스트-사용매뉴얼-11.md)과 [RemoteAssist E2E 테스트 사용 매뉴얼 12번](RemoteAssist-E2E-테스트-사용매뉴얼-12.md)대로 동작하도록 코드를 수정하는 개발 기준이다. 개요는 [README](../README.md), 정확한 명령과 필드 정의는 [사용 규약](../docs/agent-usage.md)을 따른다.

계획 작성 당시의 소스 기준은 Git `3b285ea`였다. 3절의 비교 표는 그 시점의 차이를 보존한 것이다. 현재 빌드·로컬 검사·실제 GUI 실행 결과는 아래 구현 검증 증거에 기록한다. 기존 코드가 있다는 이유로 새 동작을 구현 완료로 간주하지 않는다.

사용 방식은 11·12번 매뉴얼, 개발 순서·태스크·완료 조건은 이 문서, 실제 명령 형식은 사용 규약으로 나눈다. 서로 어긋나면 구현자가 임의로 한쪽을 따르지 말고 매뉴얼의 의도에 맞춰 관련 문서를 함께 고친다. 기존 `docs/agent-driven-desktop-control.md`는 이 문서의 안내로 정리하여 별도의 개발 순서를 유지하지 않는다.

### 확정한 동작

| 항목 | 개발 기준 |
|---|---|
| 도구의 사용자 | 코딩 에이전트다. 요청할 행동과 다음 순서 및 제품의 성공 여부를 판단한다 |
| Controller | 코딩 에이전트와 같은 PC에서 상주하며 요청·응답·이미지를 전달한다 |
| Agent | 관측하거나 조작할 PC의 로그인된 일반 사용자 바탕화면에서 실행한다 |
| 같은 PC 지원 | Controller와 Agent를 같은 PC에 함께 실행할 수 있다 |
| RemoteAssist 배치 | 작업 PC는 PC A와 같다. PC A에는 코딩 에이전트·Controller·Agent·Viewer, PC B에는 Agent·제품 대상자 프로그램·시험용 창을 둔다 |
| RemoteAssist 입력 | 시험 중 PC A의 Viewer에만 입력한다. PC B의 Agent는 관측 전용으로 사용한다 |
| 대상자 동의 | 12번 예시의 지원 승인과 즉시 종료는 사람이 직접 수행한다 |
| 파일·로그·서비스 작업 | 같은 PC에서는 로컬 명령, 원격 PC에서는 기존 SSH로 처리한다 |
| 도구가 받는 작업 | 창 조회·클릭·입력 등 GUI 명령 하나다. 시험 순서 파일은 받지 않는다 |
| 도구의 결과 | 요청 수행 결과와 관측값이다. 제품의 시험 통과 여부가 아니다 |
| 기본 지원 환경 | Windows 10/11 x64의 로그인된 일반 사용자 바탕화면이다. 관리자 창·잠금 화면·RDP 세션 지원은 별도 범위다 |

### 이번 README 수정 내용

기존 README에는 Agent를 원격 PC에만 두고 Controller와 반드시 다른 머신에 배치하는 것으로 읽히는 설명이 있었다. 같은 PC A에도 Agent를 실행하는 구조로 수정했다. 구조 그림·역할 표·사용 흐름·파일 작업 구분·매뉴얼 링크도 함께 맞췄다. 장애 시 입력 해제는 무조건 성공한다고 표현하지 않고, 독립적으로 해제를 시도하고 확인한 결과를 남기도록 정리했다.

## 2. 완성 후 실행 구조

```text
PC A = 작업 PC = RemoteAssist 지원자 PC
  코딩 에이전트
    └─ Controller.exe의 명령을 호출한다
         └─ 상주 Controller가 대상 Agent를 선택한다
              ├─ PC A의 Agent → Viewer 브라우저를 조작한다
              └─ PC B의 Agent → 대상 PC의 창과 화면만 관측한다

PC A의 Viewer → RemoteAssist 연결 → PC B의 제품 프로그램 → 시험용 창

PC A·PC B의 제품 기록은 코딩 에이전트가 로컬 명령·SSH로 수집한다
```

Controller 요청 명령을 실행한 짧은 프로세스와 계속 실행되는 상주 Controller를 구분한다. 클릭 요청의 명령 프로세스가 끝나도 상주 Controller·Agent·제어 세션은 유지한다. 이미지 분석 중에 코딩 에이전트가 주기적으로 생존 신호를 보내도록 만들지 않는다.

사용자가 배치하는 실행 파일은 Controller.exe와 Agent.exe 두 종류다. 입력 해제 감시와 버튼 정보 조회를 분리 실행해야 할 때는 같은 Agent.exe의 내부 실행 모드를 사용한다. 실행 파일 종류를 두 개로 정리하는 것이 모든 일을 하나의 프로세스에 넣는다는 뜻은 아니다.

## 4. 구현할 파일 구조

아래 경로로 구현했다. Windows 입력은 `GuiInput.cs`, 앱 소유권은 `GuiApplications.cs`, 창 표면 캡처는 `GraphicsCapture.cs`에 있다. 같은 책임을 이미 담은 파일이 있으면 새 복사본을 만들지 말고 이름과 내용을 바꾼다.

```text
src/

  Agent/               Agent.csproj, Program.cs, Agent.json
  Contracts/           GUI 요청·응답·세션·오류·통신 타입
  Core/
    ControllerHost.cs  상주 Controller와 로컬 명령 연결
    AgentHost.cs       Agent 연결·GUI 작업 실행·내부 감시 관리
    GuiRequestHandler.cs  지원 명령 확인과 단일 요청 실행
    ControlSessions.cs    세션·모드·만료·입력 소유 관리
    RequestJournal.cs     요청 수락·실행·완료 기록과 결과 조회
    WindowRegistry.cs    공개 창·요소 번호와 실제 대상의 대응
    CaptureStore.cs      캡처 번호·이미지·유효 기간 관리
    WindowsDesktop.cs, GraphicsCapture.cs, WindowsInput.cs, GuiInput.cs, GuiApplications.cs, WatchdogRunner.cs
scripts/               최초 설정·기동·중단 도구
tests/Driver.Tests/    도구 자체의 로컬 검사
fixtures/SimpleMemo/   저장·열기 동작을 가진 검증용 GUI 앱
fixtures/InputWindow/ 클릭·문자·키·휠을 기록하는 검증용 GUI 앱
```

Core·Contracts는 공통 라이브러리이며 별도 설치 프로그램으로 세지 않는다. 검증용 GUI 앱은 제품 패키지에 넣지 않는다. KnockHB의 소스·실행 파일·제품별 판정기는 이 저장소의 빌드 의존성에 추가하지 않는다.

## 5. 요청·세션·시간 관리 기준

### 5.1 공개 명령

G05에서 아래 명령을 모두 제공한다. 모든 호출은 작업 PC의 Controller에 한다.

| 명령 | 구현할 결과 |
|---|---|
| `--help` | 사용법·버전·동봉 사용 규약 위치를 안내한다 |
| `--status` | 같은 PC와 원격 PC를 포함한 연결 Agent 목록을 반환한다 |
| `--status --machine TARGET` | 대상의 바탕화면·지원 작업·제한을 반환한다 |
| `--session-open --machine TARGET --mode control 또는 observe` | 세션을 열고 실제 번호·머신·모드·만료 시각을 반환한다 |
| `--session-status [CONTROL_ID]` | 특정 세션 또는 세션 목록을 반환한다 |
| `--request FILE` | JSON 파일의 GUI 명령 하나를 수행한다 |
| `--request-status CONTROL_ID REQUEST_ID` | 원래 요청의 상태와 결과를 조회한다 |
| `--session-close CONTROL_ID` | 도구 입력을 해제하고 정해진 앱 수명에 따라 세션을 닫는다 |

세션 열기의 `--idle-seconds`도 구현한다. 최초 설정·상주 시작·중단 도구는 G03에서 별도로 제공하고, 새 명령을 사용자가 매번 직접 초기화해야 하는 구조로 만들지 않는다.

### 5.2 요청과 응답

요청 필드는 사용 규약의 `apiVersion`, `requestId`, `controlSessionId`, `operation`, `timeoutMilliseconds`, `arguments`를 사용한다. 창·요소 번호는 응답에서 받아 사용한다. 코딩 에이전트에게 내부 Windows 창 핸들이나 실행 순번을 계산하도록 요구하지 않는다.

| 응답 상태 | 의미 | 명령 종료 코드 |
|---|---|---|
| `completed` | 도구의 요청 수행이 끝났다 | 0 |
| `rejected`, `failed` | 입력 전 거부 또는 처리 중 실패다 | 1 |
| `completionUnknown` | 실제 수행 여부나 범위를 확정하지 못했다 | 2 |
| `running` | 결과 조회 시 실행 중이다 | 3 |

요청의 내용이 잘못되어 변경 전에 거부한 것과, 입력 일부를 보낸 뒤 실패한 것을 구분한다. 알려진 입력 전달 수와 입력 해제 결과는 오류에도 남긴다. 제품 성공을 뜻하는 `verdict`, `pass` 등의 판정 필드를 새 GUI 응답에 추가하지 않는다.

`--help`를 제외한 공개 명령은 UTF-8 JSON 객체 하나만 출력한다. 안내·진행 메시지는 오류 출력으로 보낸다. `--help`는 상주 Controller가 없어도 읽을 수 있어야 한다.

### 5.3 시간과 보관의 초기 기본값

| 항목 | 초기 기본값·규칙 |
|---|---|
| 세션 유휴 만료 | 900초다. 정상 수락한 새 GUI 명령으로 갱신한다 |
| 단일 GUI 요청 | 기본·최대 5초이며 1~5000밀리초를 허용한다 |
| 키·버튼 최대 유지 | 기본 1500밀리초다. 상태 응답으로 실제 값을 알린다 |
| 좌표용 캡처 유효 기간 | 초기 기본값은 30초로 두고 응답의 만료 시각을 따른다 |
| 요청 결과 최소 보관 | 초기 기본값은 24시간으로 두고 초 단위 값을 상태 응답에 알린다 |
| 요청 크기 | 기본 최대 1MiB이며 실제 제한을 상태 응답에 알린다 |

내부 생존 확인, 세션 목록·요청 결과 조회, 같은 요청의 재조회는 세션 유휴 시간을 연장하지 않는다. 키 해제와 만료를 판단하는 경과 시간은 PC 시각 변경에 영향받지 않게 측정한다. 캡처의 좌표 유효 기간이 끝나도 이미 작업 PC에 저장한 이미지를 바로 삭제하지 않는다.

5초는 제품 접속을 기다리는 전체 시간이 아니다. 코딩 에이전트가 관측 요청을 반복하며 제품 대기를 관리한다. 요청 제한 시간이 끝나도 실행되지 않았다고 단정하지 않고 기록·실제 수행 범위에 맞게 응답한다.

### 5.4 종료·시간 초과와 입력 실행의 순서

세션 상태는 `active`(사용 중), `closing`(종료 처리 중), `closed`(정상 종료), `expired`(유휴 만료), `blocked`(중단·해제 확인 미완료)로 구분한다. 종료 중이거나 차단된 조작 세션은 같은 바탕화면의 조작 자리를 계속 점유한다. 기존 작업이 더 입력하지 못하고 소유 입력이 해제됐다는 확인 전에는 새 조작 세션을 허용하지 않는다.

Agent는 세션별 GUI 변경 요청을 순서대로 실행한다. 상태·결과 조회와 독립 입력 해제는 이 대기열과 분리한다. 조작 세션 종료·만료·통신 단절 시에는 다음 순서를 강제한다.

1. 세션을 `closing`으로 기록하고 새 변경 요청을 거부한다. 이전 작업이 가진 실행 허가도 무효화한다.
2. 대기 중인 변경 요청을 실행하지 않고 결과를 기록한다. 이미 실행 중인 요청에는 중단을 알린다.
3. 실행부는 누름·이동·휠·문자 전송·앱 실행 직전에 허가와 중단 상태를 다시 확인한다. 이 확인과 실제 변경이 종료 처리와 엇갈리지 않도록 짧은 공통 잠금으로 보호한다. UI 조회·네트워크 대기처럼 오래 걸리는 작업은 이 잠금 안에서 수행하지 않는다.
4. 입력을 보낼 수 있는 작업 프로세스의 중단을 확인한 다음, 도구가 누른 키·버튼을 해제한다. 중단이 지연되면 독립 감시가 정해진 시간 안에 소유 작업 프로세스의 종료·해제를 시도한다. 무관한 앱이나 keep 앱을 함께 종료하지 않는다.
5. 입력 해제와 `session` 앱의 종료 결과를 각각 확인하여 저장한다. 성공하면 종료 원인에 따라 `closed` 또는 `expired`로 확정한다. 중단·해제를 확인하지 못하면 `blocked`로 남기고 실패·확인 불가 결과를 반환한다.

작업 중단 확인에는 기본 3초의 한도를 두고 실제 한도를 설치 설정과 상태 응답에 알린다. 이 한도는 단일 GUI 요청의 실행 시간을 연장하는 데 사용하지 않는다. 한도 내 중단을 확인하지 못하면 성공을 반환하지 않는다. 감시가 잠금을 얻지 못하거나 작업 프로세스가 응답하지 않는 경우도 차단 원인으로 남긴다.

관측 전용 세션을 닫을 때는 그 세션의 조회만 중단한다. 다른 세션·RemoteAssist·사용자가 누른 입력은 해제하지 않는다. 관측 세션 응답의 `inputReleased=true`는 그 세션에 남은 도구 소유 입력이 없다는 뜻이며 PC 전체의 키 상태를 보증하지 않는다.

`inputReleased`는 true(소유 입력이 없음을 확인), false(남은 소유 입력을 확인), null(확인 불가)로 구분한다. 관측 세션도 실행부 상태를 확인하지 못했으면 true를 추정해서 반환하지 않는다.

개별 요청의 제한 시간도 대기 시간을 포함하여 상주 Controller가 요청을 수락한 순간부터 계산한다. 기한이 지난 대기 요청은 시작하지 않는다. 이미 Agent에 전달한 요청은 중단을 요청하고 Agent 자체의 실행 시간 제한도 함께 적용한다. 분리된 PC 사이에서 중단 확인이 오지 않으면 5초가 지났다는 이유만으로 ‘실행되지 않음’이나 ‘중단 완료’를 확정하지 않는다.

실행하지 않았음이 확인되면 `rejected`, 일부 실행과 중단 범위가 확인되면 `failed`, 범위를 확정할 수 없으면 `completionUnknown`으로 응답한다. 마지막 경우에는 확인할 때까지 해당 조작 세션의 새 변경 요청을 막는다. 결과 조회로 나중에 확정할 수 있으나, 예전 요청을 다시 실행하지 않는다. 일반 요청의 시간 초과로 세션을 닫거나 keep 앱을 종료하지는 않는다.

`--session-close`의 중복 호출은 같은 종료 처리를 조회·이어받고 원래 정리 마감 시간을 연장하지 않는다. 실행 중 요청의 최종 결과를 보관하고, 닫기 응답을 잃은 호출자는 세션 상태를 조회할 수 있어야 한다. 세션 닫기 요청의 응답 대기도 기본 5초로 제한하며, 정리가 끝나지 않았으면 상태와 알려진 해제 결과를 담은 `failed` 또는 `completionUnknown`을 반환한다. 정리 작업 자체는 상주 Agent·독립 감시가 이어서 수행한다.

차단 중에도 세션·결과 조회, 명시적 세션 닫기, 독립 감시의 해제는 허용한다. 조작 세션의 `release-input`도 도구 소유 입력을 해제하는 용도로 허용하며 전경 창·유효 캡처를 요구하지 않는다. 관측 세션에는 이 예외를 적용하지 않는다. 실패 결과를 반환했더라도 미해제 소유 입력이 있으면 차단을 유지한다.

명시적 release-input도 새 누름을 잠시 막고, 대기 입력을 취소하고, 실행 중 입력의 중단을 확인한 뒤 해제한다. 앱이나 세션은 닫지 않는다. 다른 차단 원인이 없고 원래 입력 작업이 끝났으며 해제를 확인한 경우에만 새 입력을 허용한다. closing·expired 상태를 active로 되돌리지 않는다.

### 5.5 Agent 실행 기록과 공개 최종 결과의 책임

**Agent는 실제 GUI 수행 여부의 기록을, 상주 Controller는 코딩 에이전트에게 반환할 최종 응답의 기록을 소유한다.** 두 기록을 같은 것으로 취급하지 않는다. 짧은 CLI 프로세스는 요청 제출과 응답 출력만 담당하며, 그 프로세스 종료가 수락된 작업을 취소하거나 재실행하는 원인이 되지 않는다.

| 저장 위치 | 기록할 내용 | 복구 시 사용할 기준 |
|---|---|---|
| Agent | 세션·요청 번호·요청 비교값·수락/실행 상태·실제 수행 범위·입력 해제 결과·원본 캡처 정보 | 실제 GUI 작업을 다시 실행해도 되는지 판단하지 않고, 이미 확인한 수행 결과를 복원한다 |
| 상주 Controller | 공개 요청·Agent 연결 식별·Agent 수행 결과·로컬 이미지 저장 진행·공개 응답 | `--request-status`가 반환할 최신 확인 결과를 복원한다 |

일반 GUI 요청은 Agent의 확정 결과를 Controller가 저장한 뒤 공개한다. 캡처는 ‘Agent 촬영 완료 → Controller 수신·파일 검증 → 로컬 최종 파일 확정 → 공개 응답 저장’까지 진행해야 `completed`가 된다. 촬영만 끝난 결과를 공개 완료로 바꾸지 않는다. `output`은 Controller PC의 경로이며 Agent가 이 경로에 파일을 만들거나 접근하지 않는다.

캡처 중간 파일·기록은 세션과 요청에 묶고, 최종 경로에는 기존 파일을 덮어쓰지 않는 방식으로 게시한다. 파일을 검증하고 공개 응답을 저장하기 전까지는 `data.path`를 최종 성공 결과로 공개하지 않는다. 이미 게시된 최종 파일은 ‘실패 정리’라는 이유로 무조건 삭제하지 않는다.

| 실패·종료 지점 | 결과 조회·재시작 후 처리 |
|---|---|
| CLI만 종료 | 상주 Controller가 원래 마감 시간 안에서 처리를 계속하고 결과를 보관한다 |
| Agent가 촬영했지만 이미지 수신·저장 실패 | 알려진 촬영 범위를 포함한 `failed`를 공개 기록으로 저장한다. `completed`로 응답하지 않는다 |
| 로컬 최종 파일은 있지만 공개 완료 기록 직전에 Controller 종료 | 보호된 진행 기록의 요청·경로·기대 해시와 실제 파일을 검증한 경우만 완료 응답을 복원한다. 일치하지 않으면 실패 또는 미확정으로 남기고 기존 파일을 덮어쓰지 않는다 |
| Agent의 확정 결과는 있으나 Controller의 공개 응답이 없음 | 등록한 동일 Agent의 원래 기록을 조회해 공개 결과를 구성한다. 캡처는 최종 파일 검증이나 원래 남은 기한 안의 기존 이미지 수신만 허용한다. 새 입력이나 새 촬영을 요청하지 않는다 |
| Agent와 Controller의 기록만으로 실제 수행 범위를 확정할 수 없음 | `completionUnknown`으로 남기며 자동 재실행하지 않는다 |

`running`은 실제 작업이나 전송이 진행 중이라고 확인한 경우만 반환한다. `completionUnknown`은 확인이 더 필요한 상태이며, 나중에 원래 기록으로 확정된 결과가 나오면 갱신할 수 있다. 확정된 `completed`·`failed`·`rejected`는 같은 요청의 재조회로 바꾸지 않는다. 이미지 수신 실패가 확정된 요청은 결과 조회로 새 이미지 수신을 시작하지 않으며, 새 캡처가 필요하면 코딩 에이전트가 새 요청 번호를 사용한다.

두 위치 모두 약속한 결과 보관 기간을 지킨다. 캡처 좌표가 만료되거나 세션을 닫아도 최종 응답은 보관한다. Controller 재시작 시 이전 요청의 처리부터 복구하며, 중단된 조작 세션의 입력 허가를 자동 복원하지 않는다.

재시작·재연결·재조회로 원래 요청의 마감 시간을 새로 시작하지 않는다. 캡처의 원래 기한이 지났고 검증된 최종 파일도 없으면 새 전송을 시작하지 않고 실패 또는 확인한 범위의 미확정 결과를 남긴다. 결과 기록 조회 자체는 보관 기간 안에서 가능하다.

마감 기록에는 해당 PC의 단조 시각과 부팅 구분 정보를 함께 남긴다. 같은 부팅 안의 프로세스 재시작은 원래 마감을 사용하고, PC 재부팅 등으로 남은 시간을 신뢰할 수 없으면 미완료 작업을 이어 실행하지 않는다. 이미 끝난 작업의 기록 조회·확정 결과 복원은 허용하되 새 실행 기한을 만들지 않는다.

## 6. 태스크별 구현 방법과 완료 기준

### G01. 새 계약과 지원 범위

**수정 대상:** `src/Contracts/Protocol.cs`, `docs/agent-usage.md`다.

1. 실행 계획용 `RunConfig`, 제품 권한, 기존 `Wire.Version=2`를 공개 GUI 요청의 필수 입력으로 쓰지 않는다. 새 GUI API 버전은 1로 구분한다.
2. 요청·응답·세션·지원 기능·오류를 명확한 타입으로 정의한다. 알 수 없는 필드·중복 키·잘못된 타입과 크기 초과는 변경 전에 거부한다.
3. 같은 PC의 Agent와 원격 Agent는 같은 요청 계약을 사용한다. 공개 문서의 ‘원격만 지원’ 표현을 ‘대상 PC’로 맞춘다.
4. 관측 명령은 초점·창 위치·선택 상태를 바꾸지 않는 것으로 정의한다. 지원하지 않는 바탕화면과 관리자 권한 창은 원인을 반환한다.

**완료 기준:** 두 매뉴얼에 필요한 명령·데이터를 새 계약으로 표현하며 시나리오 파일이 필요하지 않다. 계약 검사가 잘못된 요청의 입력 실행을 막는다.

### G02. 프로젝트와 이름 정리

**수정 대상:** `src/Server`, `src/Client`, `src/Client.Broker`, `src/Client.Watchdog`, 솔루션, 모든 프로젝트 참조다.

1. Server 프로젝트를 Controller로, Client 프로젝트를 Agent로 이동·변경하고 실행 파일·설정·네임스페이스 관련 참조를 맞춘다.
2. Broker의 필요한 로그인 바탕화면 기동 기능을 설치·기동 도구로 옮긴다. 독립 입력 감시는 `Agent.exe --watchdog` 내부 모드로 옮긴다.
3. `ClientController`, `ControllerAgent`, `ClientStatus` 등 자체 코드 이름을 실제 역할에 맞춰 정리한다. .NET 자체 API 이름을 기계적으로 바꾸지 않는다.
4. 옛 프로젝트의 복사본이나 호환 실행 파일을 남기지 않는다. 패키지 경로·테스트 실행 파일 경로·빌드 스크립트의 필수 프로젝트 참조를 함께 수정하여 이름 변경 직후에도 빌드가 가능하게 한다. G17에서는 최종 패키지 구성과 문서 검사를 완성한다.

**완료 기준:** 새 프로젝트 경로로 로컬 빌드가 가능하고 Agent의 보조 모드를 실제로 시작할 수 있다. 이 단계의 빌드 성공을 GUI 동작 완료로 보고하지 않는다.

### G03. 최초 설정과 상주 실행

**수정 대상:** `ApplicationStartup.cs`, Controller·Agent의 `Program.cs`와 설정, `scripts/`다.

1. `Controller.json`은 접속 주소·포트·상태 저장 위치, `Agent.json`은 고유 PC 이름·Controller 주소·상태 저장 위치·로그인 세션 선택을 다룬다. 현재 하드코딩된 사설 주소·특정 PC 이름을 배포 기본값에서 제거한다.
2. 같은 PC A의 Agent는 로컬 주소로, PC B의 Agent는 PC A의 접속 주소로 같은 Controller에 연결할 수 있게 한다.
3. 두 프로그램의 상주 실행은 설정 파일을 읽어 시작한다. 로그온 세션이 없으면 GUI 지원 불가를 알리고, SSH에서 실행됐다는 이유로 바탕화면 실행에 성공한 것으로 처리하지 않는다.
4. 최초 설정·시작·상태 확인·중단·재기동을 수행할 로컬 PowerShell 도구를 제공한다. 수동 배치와 기존 SSH를 통한 파일 배치를 모두 설명한다. 예약 작업이 필요하면 ‘사용자가 로그온할 때만 실행’하며 생성한 작업만 식별해 제거한다.
5. Controller와 Agent의 상태 폴더를 분리한다. 같은 PC에 함께 설치해도 파일·잠금·포트가 충돌하지 않아야 한다.
6. 명령 프로세스 종료와 상주 프로그램 중단을 구분한다. 시작 실패·이미 실행 중·잘못된 설정을 구체적으로 알린다.
7. 현재 .NET 10·WPF 설정을 유지한다. 실행에 필요한 .NET Desktop Runtime 유무를 최초 설정에서 확인한다. 기존 설정·연결 등록을 덮어쓰는 갱신은 백업과 복원 경로를 제공한다.

**완료 기준:** 설치 폴더에 수동 배치한 뒤 문서만으로 시작·중단할 수 있다. GUI 명령마다 재설치하거나 서명된 시험 실행 파일을 새로 만들 필요가 없다.

### G04. 통신과 연결 대상 확인

**수정 대상:** `ControllerAgent.cs`, `ControllerWire.cs`, `PersistentAgent.cs`, `ManagedAgent.cs`, 연결 설정이다.

1. Agent가 상주 Controller로 연결하는 기존 구조와 메시지 크기 제한·직렬 전송을 재사용한다. 동일 PC도 같은 연결 경로를 사용한다.
2. PC 이름만 보낸 연결을 신뢰하지 않는다. 최초 설정에서 Controller와 Agent의 통신용 인증서를 만들고 상대 인증서 정보를 등록하여, 암호화된 연결에서 서로 등록한 상대인지 확인한다. 인증서·키를 매 시험마다 다시 발급하지 않는다.
3. PC 이름과 등록한 상대 정보를 묶는다. 서로 다른 두 Agent가 같은 PC 이름을 주장하면 거부하고 이유를 기록한다. 개인키는 해당 사용자만 읽을 수 있는 저장소에 둔다.
4. 로컬 명령 연결은 현재의 같은 Windows 사용자만 접근 가능한 통신 경로를 유지한다. 원격 GUI 연결과 로컬 명령의 권한을 구분한다.
5. 연결 단절 시 새 입력을 막고 독립 입력 해제를 시작한다. 재연결은 통신 복구만 하며 이전 GUI 명령을 자동 재실행하지 않는다.

**완료 기준:** 로컬 통신 검사에서 A·B 역할의 연결이 동시에 목록에 나타난다. 등록되지 않은 연결·동일 이름 충돌·다른 PC로 향하는 세션 요청은 실행 전에 거부된다. 재연결로 모의 입력이 반복되지 않는다. 실제 두 PC 연결은 G21에서 확인한다.

### G05. Controller 공개 명령

**수정 대상:** Controller의 `Program.cs`, `ApplicationStartup.cs`, `ControllerCli.cs`, 상주 Controller 요청 처리다.

1. 5.1절의 명령·옵션을 모두 구현한다. 명령행 인자는 공개 규약대로 검사한다.
2. 상태 조회에는 실제 지원하는 작업만 반환한다. 문서에 있는 작업이 미구현이면 지원한다고 표시하지 않는다.
3. 요청 파일은 작업 PC에서 읽고, 파일을 그대로 대상 PC의 셸에 전달하지 않는다. GUI 명령 하나만 해석한다.
4. Controller 부재·대상 Agent 단절·지원하지 않는 버전·잘못된 파일을 JSON 오류와 규약의 종료 코드로 반환한다.

**완료 기준:** 명령을 별도 프로세스로 여러 번 실행해 같은 세션에서 이어 쓸 수 있다. 출력 앞뒤에 배너나 로그가 섞이지 않는다.

### G06. 세션과 관측 전용 모드

**수정 대상:** 새 `ControlSessions.cs`, 상주 Controller·Agent의 세션 관리, 기존 `RunStore` 의존부다.

1. 세션 번호를 머신·Windows 사용자·로그인 세션·바탕화면·모드에 묶고 Agent에서도 다시 확인한다.
2. 같은 바탕화면의 조작 세션은 하나로 제한한다. 관측 세션은 별도로 둘 수 있지만 읽기 전용을 Agent 실행부에서 강제한다.
3. 관측 모드에서는 `windows`, `controls`, `capture`, 상태·결과 조회만 허용한다. `focus`, 앱 실행·종료, 입력 해제 등 변경 요청은 실제 처리 전에 거부한다.
4. 화면·요소 조회가 전경 창을 바꾸거나 입력 감시를 통해 RemoteAssist의 정상 입력을 끊지 않게 한다. PC B의 제품 입력을 도구 자신의 입력으로 기록하지 않는다.
5. 기본 900초 유휴 만료·닫힌 세션·중복 종료·세션 생성 응답 유실 후 목록 조회를 구현한다.
6. 로그인 세션이나 바탕화면이 바뀌면 기존 제어를 유효한 것으로 유지하지 않는다. Controller 재시작 후 세션을 무조건 복원하지 않고 종료·미확정 결과와 실제 Agent 상태를 확인한다.
7. 닫기·유휴 만료·통신 단절·중단 요청은 5.4절의 공통 종료 절차를 따른다. 종료가 시작된 뒤 새로운 입력이 끼어들 수 없도록 Agent가 상태 변경과 실제 입력 직전 확인을 같은 순서로 처리한다.

**완료 기준:** 로컬 통신·모의 입력 검사에서 A 조작과 B 관측을 구분하고, 관측 모드 변경 요청과 종료 후 입력을 거부한다. 실행 중 요청과 종료가 겹치는 검사도 통과한다. 실제 두 PC 확인은 G21에서 수행한다.

### G07. 요청 기록과 응답 유실

**수정 대상:** 새 `RequestJournal.cs`, `CommandEngine.cs`, Agent·Controller의 결과 보관이다.

1. 요청 번호를 세션 안에서 유일하게 사용한다. 기본값을 적용하고 속성 순서를 정리한 요청 내용으로 동일 여부를 비교한다. 공백·속성 순서 차이를 다른 요청으로 처리하지 않는다.
2. 상주 Controller는 Agent로 보내기 전에 공개 요청·중복 비교값·마감 시각을 기록한다. Agent는 입력 전에 ‘수락됨’을 확정 기록하고 실행 시작·완료·실패를 기록한다. 기록을 쓰지 못하면 새 입력을 시작하지 않는다. 실행 기록과 공개 최종 응답의 책임은 5.5절을 따른다.
3. 같은 번호·같은 내용은 실행 중 상태 또는 원래 결과를 반환한다. 같은 번호·다른 내용은 `DuplicateRequestMismatch`로 거부한다.
   중복 요청 판별은 캡처 출력 파일 존재 여부 검사보다 먼저 한다. 이미 완료한 캡처의 재조회가 `OutputExists`로 바뀌면 안 된다.
4. 수락된 요청이 실행됐을 수도 있으나 완료 기록이 없으면 재시작 후 `completionUnknown`으로 남긴다. 명확히 실행 중인 요청만 `running`으로 표시한다.
5. Controller가 결과를 받았으나 명령 호출자가 받지 못한 경우에도 `--request-status`로 원래 결과를 읽을 수 있게 한다. 닫힌 세션의 결과도 보관 기간 동안 조회한다.
6. 결과 조회와 입력 해제는 느린 GUI 요청의 실행 대기열에 막히지 않게 한다. 보관 공간 부족은 입력 전에 알리고, 보관을 약속한 기록을 조용히 지우지 않는다.
7. 일반 로그에는 요청 본문·입력 문자·PIN을 그대로 남기지 않는다. 중복 비교에 필요한 원문 보관은 최소화하고 제한된 저장소를 사용한다.
8. 새 관측은 항상 새 요청 번호로 실행한다. 기록이 없거나 보관 기간이 끝난 요청은 ‘입력이 실행되지 않았다’고 판단하지 않는다. 원래 실행 여부를 확인할 수 없으면 새 입력 전에 재관측하고 시험 중단 여부를 판단한다.
9. 같은 요청이 동시에 도착하면 한 번만 수락한다. 같은 번호의 처리·결과 저장을 묶어 보호하여 두 호출이 각각 입력을 실행하지 못하게 한다. 완료·실패·거부가 확정된 공개 응답은 재조회 때 바꾸지 않는다. 미확정 응답만 나중에 확인한 결과로 갱신할 수 있다.

**완료 기준:** 모의 입력과 실제 로컬 프로세스·파일을 사용해 응답 유실·동시 중복·재시작 검사를 통과한다. 입력 완료와 이미지 전달 완료를 다르게 처리하고, 수락 기록이 있는 입력을 자동 재실행하지 않는다. 실제 OS 입력을 포함한 확인은 G20·G21에서 수행한다.

### G08. 창 검색과 식별

**수정 대상:** `WindowsDesktop.Inspect/Identify`, 새 `WindowRegistry.cs`다.

1. 접근 가능한 일반 사용자 창을 조회하고 창 번호·제목·프로그램 번호·생성 시각·실행 경로·위치·전경 여부를 반환한다. 창을 찾기 전에 제목·해시 목록을 시험 실행 파일로 제출하게 만들지 않는다.
2. 공개 창 번호는 세션 내부의 실제 창 정보에 대응시킨다. 창 핸들이 재사용되거나 프로세스가 바뀌면 옛 번호를 거부한다.
3. 저장·열기 같은 대화상자가 별도 창으로 뜨는 경우도 조회한다. 제목이 바뀌었다는 이유만으로 동일한 앱의 모든 관측을 끊지 않는다.
4. 열 수 없는 창이 있어도 다른 창의 조회는 유지한다. 찾을 수 없음과 접근 권한 부족을 구분한다.

**완료 기준:** 모의 창 목록과 식별 변경 검사에서 메모·대화상자·브라우저를 구분하며, 예전 창 번호로 다른 대상에 입력하지 않는다. 실제 Windows 창과 저장·열기 대화상자 검색은 G20·G21에서 확인한다.

### G09. 버튼·입력칸·표시 값

**수정 대상:** `WindowsDesktop.Controls/ReadControls`, `UiNode`, 새 요소 번호 관리다.

1. Windows가 제공하는 UI 정보에서 요소 번호·AutomationId·이름·종류·사용 가능 여부·위치를 읽는다. AutomationId는 프로그램이 버튼에 붙인 식별 이름이다.
2. 읽을 수 있는 일반 입력칸은 문자 값도 반환한다. 현재처럼 모든 편집 내용을 일괄 숨기지 않는다. 암호·읽기 미지원은 `available=false`와 이유로 구분한다.
3. 요소 위치를 창 내부 픽셀 좌표로 변환한다. 중복된 이름·식별값은 첫 항목을 임의로 선택하지 않고 모호함을 반환한다.
4. 응답하지 않는 UI 정보 조회는 별도 Agent 보조 프로세스의 제한 시간으로 중단한다. 그 실패가 캡처·입력 해제 전체의 실패가 되지 않게 한다.
5. 웹 영상 속에 그려진 PC B 버튼은 PC A의 실제 버튼 요소로 취급하지 않는다. 이런 경우에는 캡처 좌표를 사용한다.

**완료 기준:** UI 정보 변환·조회 실패의 로컬 검사에서 일반 값과 읽기 불가·암호 값을 구분하고, 버튼 정보 실패가 별도 캡처를 막지 않는다. 실제 Windows UI 값과 캡처 좌표 조작은 G20·G21에서 확인한다. 이번 G22는 Viewer 역할의 도구 계약 모의 검사이며 실제 제품 영상 조작은 제외한다.

### G10. 관측용 창 캡처와 이미지 전달

**수정 대상:** `WindowsDesktop.Capture`, `CommandEngine.Snapshot`, `ControllerCli.SaveFrame`, 새 `CaptureStore.cs`다.

1. 캡처 요청이 몰래 `focus`를 실행하지 않게 한다. 현재의 ‘전경 창만 허용’ 조건과 전경 변화 자체를 레이아웃 변경으로 보는 조건을 관측 목적에 맞춰 분리한다.
2. 창의 클라이언트 영역을 Windows Graphics Capture로 1:1 촬영한다. 일반 불투명 가림은 거부하며 Windows 필기용 투명 레이어 등 다른 창의 픽셀을 합성하지 않는다. 클라이언트 영역은 제목 표시줄을 제외한 앱 내용 영역이다. 뒤에 있는 창도 실제로 온전히 보이면 초점을 바꾸지 않고 읽을 수 있어야 한다.
3. G20에서 전체 화면 크기의 Windows 필기용 마우스 통과 레이어가 항상 가림으로 인식되는 문제를 확인하여 화면 복사 방식을 창 표면 캡처로 교체했다. 일반 불투명 가림·최소화·화면 밖 상태를 확인한다. 정확한 이미지를 보장할 수 없으면 관측 불가를 반환한다. 숨겨진 창까지 캡처한다고 주장하지 않는다.
4. PC B는 시험 준비 때 필요한 창과 공유 표시가 보이도록 배치한다. 승인·종료로 전경이 바뀌어도 관측 명령 자체가 제품의 전경 상태를 바꾸지 않아야 한다.
5. 캡처와 UI 정보 조회를 독립시킨다. 버튼 정보를 읽지 못해도 이미지가 있으면 전달한다. 완전히 검은 화면이라는 이유만으로 항상 오류로 단정하는 현재 조건도 실제 검은 앱 화면과 구분하도록 수정한다.
6. 창 내부 물리 픽셀 기준 1:1 PNG, 캡처 번호·크기·좌표 기준·촬영 시각·유효 시각을 반환한다. 배율·음수 모니터 위치에서도 같은 규칙을 유지한다.
7. Controller가 원격 이미지를 분할 수신하고 크기·해시를 확인한 다음 작업 PC의 지정 경로에 새 파일로 저장한다. 같은 PC A의 캡처도 동일한 결과 형식으로 처리한다.
8. 기존 출력 파일은 덮어쓰지 않는다. 상주 Controller가 이미지 수신·파일 저장·공개 응답의 영속 저장까지 담당한다. 짧게 실행되는 CLI가 중간에 종료되어도 이 처리를 맡기지 않거나 취소하지 않는다. `completed`와 `data.path`는 5.5절의 저장 확인을 끝낸 경우에만 반환한다.
9. 캡처 요청 제한 시간에 이미지 전달까지 끝나지 않으면 실패·알려진 수행 범위를 반환한다. 새 요청 번호로 새 캡처를 할 수 있지만 같은 번호의 결과 조회로 새 촬영을 수행하지 않는다.

**완료 기준:** 로컬 검사에서 캡처가 창 활성화를 호출하지 않고 UI 조회 실패와 독립적으로 이미지를 전달한다. 이미지 수신·저장·확정 기록의 각 단계 실패와 CLI·상주 Controller 종료 후 재조회를 검사한다. 실제 창·브라우저 영상의 내용과 전경 유지 확인은 G20·G21에서 수행한다.

### G11. 창 활성화와 클릭

**수정 대상:** `WindowsDesktop.Focus`, `DesktopActions`, `CommandEngine.Guard/Inject`, 창·요소 번호 관리다.

1. 창 활성화는 `focus`에서만 수행하고 성공 여부를 전경 창과 대조한다. 클릭·문자 입력이 자동으로 다른 창을 활성화하지 않게 한다.
2. 클릭 대상은 요소 번호·AutomationId·좌표 중 정확히 하나로 정한다. 비활성·사라진·여러 개가 일치하는 대상을 거부한다.
3. 좌표 입력은 해당 창의 실제 캡처 번호·유효 기간·창 위치와 크기·모니터 배율을 검사한다. 화면 전체 좌표와 창 내부 좌표를 혼용하지 않는다.
4. `focus`만 바뀌었고 창 위치·배율이 같다면 캡처를 무조건 폐기하지 않는다. 내용이 동적으로 바뀌는 영상은 코딩 에이전트가 다시 관측하도록 설명한다.
5. 왼쪽·오른쪽·가운데 버튼의 누름과 해제를 한 요청에서 수행한다. 일부만 수행하면 전달 수와 해제 결과를 남긴다.

**완료 기준:** 자체 입력 확인 창에 대응하는 모의 관측·입력 검사에서 클릭 한 번의 누름·해제와 전경·대상·배치 오류 차단을 확인한다. 실제 저장 버튼과 캡처 좌표 클릭은 G20·G21에서 확인한다. 이번 G22는 A의 Viewer 역할에만 입력하는 모의 계약 검사이며 실제 RemoteAssist 영상 속 버튼 전달은 제외한다. G11 완료에 RemoteAssist 실행을 요구하지 않는다.

### G12. 문자와 키보드 입력

**수정 대상:** `CommandEngine.ValidateInput/Inject`, `WindowsInput`, `Input.cs`다.

1. 문자 길이를 규약의 1~4096자에 맞춘다. 현재 256자 제한과 맞지 않는 부분을 수정한다. 한글·영문·한 쌍의 UTF-16 코드로 표현되는 문자도 손상 없이 보낸다.
2. 현재 선택된 입력 대상에 문자를 전달한다. 입력칸 선택은 코딩 에이전트가 별도 클릭으로 수행한다. 직접 값 대입으로 제품의 키보드 입력 시험을 대신하지 않는다.
3. Enter·Tab 같은 제어 키는 문자 문자열과 분리한다. 규약의 키 이름을 실제 키로 변환하고 임의 숫자 키 코드를 공개 필수 입력으로 요구하지 않는다.
4. `key`의 press·down·up, `chord`의 키 조합을 구현한다. 일반 누름·키 조합은 요청 안에서 해제까지 끝낸다.
5. 입력 전에 도구 소유 누름을 기록하고, 전송 실패·취소 시에도 해제를 수행한다. 사용자가 이미 누르고 있는 키를 도구가 가져와 해제하지 않는다.

**완료 기준:** 모의 입력 검사에서 한글·영문·복합 문자의 전송과 Enter·Tab·Ctrl+A·F12의 누름·해제를 확인한다. 실제 OS 입력은 G20·G21에서 확인한다. 이번 G22는 시험용 Viewer 중계 스텁을 통한 문자·F12 계약 검사이며 실제 RemoteAssist 전달은 제외한다. G12 완료에 RemoteAssist 실행을 요구하지 않는다.

### G13. 이동·끌기·휠

**수정 대상:** `WindowsInput`, `InputController`, 마우스 명령 처리다.

1. 이동·휠은 유효 캡처와 창 내부 좌표를 사용한다. 휠 방향·범위는 사용 규약과 맞춘다.
2. 끌기는 시작·끝 좌표와 최대 단계 수를 검사하고, 도중 취소·창 변경·시간 초과가 생기면 누른 버튼부터 해제한다.
3. 각 입력 구간에서 세션·대상 창·중단 상태를 확인한다. 무한 반복이나 장시간 버튼 유지가 발생하지 않게 한다.

**완료 기준:** 모의 입력 검사에서 이동·휠·끌기 좌표와 도중 중단 시 버튼 해제를 확인한다. 실제 입력 확인 창의 결과는 G20에서 별도 짧은 회차로 확인한다. 이 항목을 12번 기본 RemoteAssist 시험에 임의로 추가하지 않는다.

### G14. 앱 실행과 유지 정책

**수정 대상:** `OwnedApplications`, `InputController.Cleanup`, `PersistentAgent.EndLocked`, 실행 요청 처리다.

1. 대상 PC의 절대 실행 경로·문자열 인자 배열로 실행한다. 셸 문자열로 합치거나 작업 PC의 경로로 착각하지 않는다.
2. 새 프로세스 생성 시 실제 프로그램 번호·생성 시각·경로·소유 세션을 기록한다. 프로그램 번호만 같다는 이유로 기존 앱이나 다른 앱을 종료하지 않는다.
3. 기본 `lifetime=keep` 앱은 세션·요청 프로세스·GUI 보조 프로세스가 종료되어도 유지한다. 현재 작업 묶음 핸들을 닫으면 앱이 종료되는 설정을 제거·분리한다.
4. `lifetime=session` 앱은 세션 종료·만료 시 해당 소유 앱만 종료한다. 두 정책을 별도 작업 묶음으로 관리하여 keep 앱이 같이 종료되지 않게 한다.
5. `close-window`는 창 닫기 요청 전달까지만 보장한다. 저장 대화상자·종료 거부가 있으면 코딩 에이전트가 다시 관측한다. `terminate-owned`는 지정한 세션 소유 앱만 종료한다.
6. 입력 해제 완료와 앱 종료 완료·유지를 별도 결과로 반환한다. keep 앱이 남았다는 이유로 다음 세션을 막지 않는다. 종료 실패 앱은 기록에 남기고 해결 전 소유권을 잃지 않는다.

**완료 기준:** GUI 입력 없는 로컬 프로세스 검사에서 keep 앱은 유지되고 session 앱만 종료되며 무관한 프로세스는 살아 있다. 실제 GUI 앱의 유지·재관측은 G20에서 확인한다.

### G15. 오류 복구와 독립 입력 해제

**수정 대상:** `CommandEngine` 오류 처리, `Input.cs`, `WatchdogRunner`, Agent 내부 실행 모드다.

1. 없는 창·오래된 요소·모호한 버튼·오래된 캡처 등은 해당 요청만 거부하고 재관측이 가능하게 한다. 모든 오류에서 실행 전체와 앱을 정리하는 현재 경로를 바꾼다.
2. 데스크톱 변경·통신 단절·Agent 장애·입력 해제 실패는 새 입력을 막는 중단 원인으로 다룬다. 계속 읽을 수 있는 상태와 결과 조회는 가능한 범위에서 유지한다.
3. Agent와 독립 감시 사이에 내부 생존 신호를 유지한다. 느린 UI 정보 조회나 개별 CLI 종료가 감시 신호를 끊지 않게 한다.
4. 키·버튼 최대 유지 시간이 지나면 도구 소유 입력을 해제한다. 상태 조회로 제한 시간을 늘리지 않는다. 세션의 유휴 만료는 이 제한과 별개다.
5. 해제 실패 항목은 기록에서 지우지 않는다. 실제 확인 전에는 `inputReleased=true`로 응답하지 않는다. 정상 해제·부분 실패·확인 불가를 구분한다.
6. Agent 본체와 감시 프로세스가 각각 종료되는 경우를 검증한다. OS 전체 정지·로그아웃 등 관측할 수 없는 상태를 복구 성공으로 보장하지 않는다.
7. 세션 종료·요청 제한 시간 초과 중에도 추가 누름이 발생하지 않는지 5.4절 기준으로 검사한다. 해제를 방해하는 입력 작업 프로세스는 실제 소유 정보를 확인해 중단하며, 응답하지 않는 프로세스나 해제 실패를 남긴 채 새 조작 세션을 열지 않는다.

**완료 기준:** 로컬 프로세스와 모의 입력 검사에서 오류 후 조회·본체/감시 장애·동시 종료·시간 초과·keep 앱 유지가 동작한다. 실제 OS의 키·버튼 해제와 정상 복귀는 G20에서 별도 준비한 회차로 확인한다.

**수정 대상:** 시나리오·제품 판정·배포 전용 코드와 참조다.

### G17. 패키지와 로컬 검증 스크립트

**수정 대상:** `build.ps1`, `verify.ps1`, 솔루션·프로젝트 참조·의존 패키지 잠금 파일이다.

1. Controller용과 Agent용을 각각 독립적으로 복사 가능한 패키지 폴더로 만든다. 각 폴더의 루트에 해당 실행 파일·필요한 DLL·설정·`README.md`를 두고, `scripts/`에 해당 역할의 설치·기동 도구를 둔다. 각 폴더의 문서 구조는 아래 표를 따른다.
2. 오래된 README 복사 경로와 시나리오·fixture·전용 SSH·inventory 묶음을 제거한다. 검증용 GUI 앱은 별도 테스트 산출물로 만든다.
3. 파일 목록·크기·해시와 GUI API 버전을 기록한다. 완성했다고 표시한 명령이 해당 배포본에 실제로 존재하는지 확인한다.
4. `verify.ps1`은 빌드·명령 계약·통신·세션·패키지 검사를 로컬에서 수행하도록 바꾼다. 더 이상 필요하지 않은 Python 환경을 선행 조건으로 요구하지 않는다.
5. 실제 화면·키보드 사용은 기본 로컬 검사에서 자동 시작하지 않는다. 별도 실행 단계에서 대상·범위·결과를 명시한다. CI는 사용자의 별도 요청 전에는 생성·수정·실행·진단하지 않는다.

### G22. RemoteAssist 사용 경로의 도구 계약 모의 검증

사용자가 실제 RemoteAssist 시험을 제외하고 가상 시뮬레이션으로 가능 여부만 확인하도록 지시했다. 이번 완료 조건은 실제 Controller·인증 통신·A 조작 세션·B 관측 세션을 모의 데스크톱 및 시험용 중계 스텁과 연결하여 다음을 확인하는 것이다.
